Syllabus practical modules: 7 and 3 — functions, and arrays in their multi-dimensional form.

Evaluation: This lab is graded. It carries the same weight as the other labs inside the 20% lab component.

Only the exercises carry marks:

  • five fill-in-the-blank programs, b1 to b5, worth 5 marks each
  • five checked problems, e1 to e5, worth 10 marks each

That is 75 marks from the programs. The remaining 25 marks come from observed work and a short viva, in which you will be asked to explain your own code. The ten drills are not marked at all.

You may work in teams of one or two. If you are a pair, swap who types at the halfway point.

Lab manual: The C Programming Laboratory is the department’s shared reference. It is useful today for vim (§1) and for the compilation model (§2.5) if you still find those awkward. It does not cover functions, pointers or arrays, so it cannot help you with this week’s material. Use the Week 09 notes instead. This sheet is written to be complete on its own.

You will have attended both of this week’s lectures before this lab: Monday on functions, scope and pointers, and Tuesday on the Game of Life. Nothing in this lab is ahead of those lectures.

The Week 09 notes contain countNeighbours and nextGeneration written out in full, and you are meant to have them open while you work. What the notes do not contain is a complete program that reads a world from the input, answers one question and stops. Writing that program is your job today.

What this lab is about

There are three facts about how C passes arguments to a function. Every problem today uses one of them.

1. C passes arguments by value. When you call a function, it receives a copy of each argument. If the function assigns a new value to a parameter, the caller’s variable does not change.

2. To let a function change a caller’s variable, pass the address of that variable. You write &x at the call, and you declare the parameter as a pointer, for example int *p. Inside the function, *p refers to the caller’s variable, so assigning to *p changes it.

This is what b2_swap.c needs. It is also how b3_minmax.c gives back two answers, because a function can only return one value.

3. An array argument is converted to a pointer. When you pass an array to a function, C converts the array name to a pointer to its first element. The function therefore does not receive a copy of the array, and it can change the caller’s elements. You do not write & when passing an array.

This is why countNeighbours(world, i, j) has no & in it, even though swap(&a, &b) does.

Three drills worth doing first

Three of the ten drills demonstrate exactly those three facts. Do them in this order, and write down what you think each will print before you run it.

How to work on one problem

The steps are the same for all ten problems. Using b1_sumto.c as the example:

vim b1_sumto.c          # open the file and fill in the blank
gcc b1_sumto.c -o b1    # compile it; -o b1 names the program b1
./b1 < b1_sample.txt    # run it on the sample input
./check.sh b1           # once it runs, have it marked

Compile with plain gcc. You do not need -lm or any other flag. You may not use math.h in any problem this week; if you find yourself calling sqrt or cos from the library, you have skipped the exercise.

Compile and run the program yourself before you run ./check.sh. Running it shows you what your program actually does. The checker only tells you whether the final answer is right. You need both, and running it yourself is faster.

Every problem has a ready-made input file

Some problems need a lot of input. e3, e4 and e5 each read an 8 × 8 world, which is sixty-four integers, and e2 reads sixteen. You are not expected to type these.

Every problem has an input file next to it in your workspace. The files are all named the same way:

<problem>_sample.txt

So the command always has the same shape. The < sign tells the shell to feed the file to the program in place of the keyboard:

./b1 < b1_sample.txt          ./e1 < e1_sample.txt
./b2 < b2_sample.txt          ./e2 < e2_sample.txt
./b3 < b3_sample.txt          ./e3 < e3_sample.txt
./b4 < b4_sample.txt          ./e4 < e4_sample.txt
./b5 < b5_sample.txt          ./e5 < e5_sample.txt

Each file contains the EXAMPLE that is printed at the top of that starter file. So if your program is correct, running it on its sample file prints exactly the answer the specification promised you. For instance:

$ ./e3 < e3_sample.txt
neighbours=3
$ ./e5 < e5_sample.txt
alive=5
$ ./e4 < e4_sample.txt
........
........
...#....
...#....
...#....
........
........
........

e3 and e5 each read one more number after the sixty-four: e3 reads the row and column of the cell you are asking about, and e5 reads how many generations to run. Their sample files already contain that extra number.

This is why you should use e3_sample.txt rather than a file containing only a world. If you give e3 a world and nothing else, it reads the world and then waits for a cell that never arrives. The program looks as though it has frozen, but it is simply waiting for input.

There is one extra world file, glider.txt. It contains a shape that moves across the grid instead of staying in place. Try it with e4:

./e4 < glider.txt

You can also make your own worlds. Copy any sample file, change the 0s and 1s in it, and run it again:

cp e4_sample.txt mine.txt
vim mine.txt
./e4 < mine.txt

Act 2 · Fill in the blanks (25 minutes, 5 marks each)

In all five of these programs, the first line of the function is already written for you, and main already calls it correctly. Do not change either of them. Your job is to write the body of the function.

File What the program must do Its last line must end with
b1_sumto.c add up 1 + 2 + … + n inside a function that returns the total total=<S>
b2_swap.c exchange the caller’s two integers a=<B> b=<A>
b3_minmax.c find both the smallest and the largest of n values lo=<L> hi=<H>
b4_rowsum.c add up row r of a 4 × 4 grid sum=<S>
b5_cos.c compute cos x from the first n terms of its series cos=<V>, printed with %.6f

The function headers you are given are:

int sumTo(int n)
void swap(int *a, int *b)
void minMax(int a[], int n, int *lo, int *hi)
int rowSum(int m[][COLS], int r)
double cosSeries(double x, int n)

Each starter file begins with a comment block. Read it. The GIVEN line tells you exactly what input the program will receive and the range of each value. The ENSURES line tells you what the output must look like.

b4 is worth stopping to think about. In the parameter int m[][COLS], you may leave out the number of rows, but you may not leave out the number of columns. To find m[r][j], the machine computes r * COLS + j. Without COLS, there is no calculation it can do.

b5 contains a trap that is easy to fall into. Do not compute each term’s factorial with its own inner loop. 13! is larger than an int can hold, so the result silently becomes wrong while still looking reasonable.

Instead, build each term from the one before it:

term = term * (-x*x) / ((2*k+1) * (2*k+2));

starting with term = 1.0. Written this way, no factorial is ever calculated, and nothing overflows.

A short introduction to the Game of Life

The last three problems are all about the same thing, so here is what it is. Tuesday’s lecture covered this, and §10 to §16 of the Week 09 notes have it in full, with the code.

The Game of Life was invented by the mathematician John Conway in 1970. It is not a game anyone plays. There are no players and no moves. You set up a starting position, and from then on it runs by itself.

The world is a grid of cells. In this lab it is 8 rows by 8 columns. Each cell is either alive or dead, which we store as 1 or 0.

Neighbours. Every cell has up to eight neighbours: the cells immediately above, below, left, right, and the four diagonals. Cells at the edge of the grid have fewer, because some of those positions are outside the world. A corner cell has only three.

The rule. To work out the next generation, look at every cell and count how many of its neighbours are currently alive. Then:

If the cell is and its live neighbours number it becomes
alive 2 or 3 alive
alive anything else dead
dead exactly 3 alive
dead anything else dead

A cell can be described loosely as dying of loneliness with fewer than two neighbours, and of overcrowding with more than three. Three live neighbours around an empty cell produce a new live cell.

A generation is one application of that rule to every cell in the grid. All the cells change at the same instant, which is the point e4 is marked on: every cell must be decided from the world as it was before this generation began.

Two starting positions you will meet today. A blinker is three live cells in a row. It turns into three live cells in a column, then back again, forever. A glider is a five-celled shape that repeats itself every four generations, one square diagonally from where it started, so it appears to travel across the grid. Both are in your workspace, as e4_sample.txt and glider.txt.

That is the whole game. Nothing else happens, and no cell can see further than one step away.

Act 3 · The five checked problems (55 minutes, on your own, 10 marks each)

For these five you are given the specification and nothing else. You write the whole program.

Problem What the program must do Its last line must end with
e1.c find the value x ≥ 0 for which x³ + x = a root=<R>, printed with %.4f
e2.c print a 4 × 4 grid flipped about its diagonal (the whole output is checked)
e3.c count how many of the eight cells touching (r, c) are alive neighbours=<N>
e4.c print one generation of the Game of Life (the whole grid is checked)
e5.c count how many cells are alive after g generations alive=<N>

Notes on each problem

e1. There is no formula you can rearrange to get the answer. Use the halving method from Monday’s lecture instead. The answer lies somewhere between 0 and a.

Write the program as two functions. The first must be zero at the answer, so it is x*x*x + x - a, not x*x*x + x. The second does the halving and calls the first. If you leave out the - a, your function is zero at x = 0, the halving test is satisfied immediately, and the answer collapses to 0.0000 for every input.

e2. Build the flipped grid in a second array and print that. If you write the flipped values back into the original array as you go, you will overwrite values you have not read yet and the answer will be wrong. This is a small version of the problem e4 has.

e3. Two things can go wrong here, and only one of them is obvious.

The obvious one is that a cell must not count itself.

The other one is the edge of the grid. A corner cell has only three neighbours, not eight. If you try to look at all eight without checking, you will read outside the array. C does not stop you from doing this, and the program will often appear to work, which is what makes it dangerous.

e4. See the warning below. This is the central problem of the lab.

e5. Be careful when g is 0: the answer is the world exactly as it was given to you. A loop written to run once and then test will run once even when it was asked for no generations at all.

If you find yourself writing out the rules of the game a second time for this problem, stop. e4 already contains them.

e3, e4 and e5 are deliberately the same program, extended twice.

Write countNeighbours for e3. Copy it into e4 and use it there. If you then put the code that produces one generation into a function of its own, e5 needs only a few more lines: call that function g times, then count the live cells.

This is what e4 is marked on. Every cell in a generation must be decided from the same old world.

So you need two grids. Work out the entire next generation into a second grid, and only then copy it back into the first.

If instead you write each cell’s new value straight into world, then when you reach cell (0,1) one of its neighbours has already been changed, and it counts the wrong number. The blinker will visibly fall apart instead of flipping.

Tuesday’s lecture printed a live cell as ## and a dead cell as two spaces, which is easy to read on a projector. In this lab, print # for a live cell and . for a dead one. The checker compares text, and it cannot tell blank space apart from missing output.

How the checking works

When you run ./check.sh e3, it compiles your source file and runs it on two kinds of input: a fixed set chosen in advance, and a set generated fresh at that moment from the range in the GIVEN line. The fixed ones are labelled public and the generated ones random.

The examples printed in your starter are among the fixed ones, but there are more fixed vectors than printed examples — e3 has six, for instance. So passing the printed example does not mean passing every public vector.

This means a program that only reproduces the printed example will fail as soon as a new input is drawn.

e2 and e4 are checked over their whole output, not just the last line, because the answer is a grid rather than a single value.

Several spaces in a row count as one, so the column alignment in e2 is up to you. But a space is not the same as no space: for e4, printing # . # . instead of #.#. is a different line and fails. Print the eight characters of each row with nothing between them.

Print nothing but the grid. Do not print a prompt. The whole output is compared, so a prompt on a line of its own becomes a wrong first row and costs all ten marks — even if every cell below it is right.

If your output looks right but the check fails, run ./check.sh e4 and read the difference it prints. It shows you the line that differs, what you printed, and what was expected.

Act 4 · Check your marks, fix, and submit (10 minutes)

./check.sh          # check everything
./check.sh e4       # check one problem, while you are still working on it

check.sh prints your marks, problem by problem:

  YOUR MARKS SO FAR   (blanks 5 each, checked 10 each)

    b1  6/6 vectors    5 of  5 marks
    b2  6/6 vectors    5 of  5 marks
    b3  7/7 vectors    5 of  5 marks
    b4  6/6 vectors    5 of  5 marks
    b5  10/10 vectors    5 of  5 marks
    e1  9/9 vectors   10 of 10 marks
    e2  5/5 vectors   10 of 10 marks
    e3  9/9 vectors   10 of 10 marks
    e4  2/7 vectors    3 of 10 marks
    e5  0/9 vectors    0 of 10 marks
    ---------------------------------------------
                      58 of 75 marks

In that example, e4 has the two-grid bug described above: two of its seven test cases pass and five do not.

Marks are given per test case, not all-or-nothing. Every case you pass earns its share, so fixing one failing case is always worth doing, even in the last few minutes.

Treat the total as an estimate. Some of the test cases are generated fresh each time you run the checker, so the number can move by a mark or two between runs.

Keep fixing and re-checking. When you are finished, or when time is called, make your bundle:

./check.sh --bundle

The bundle is written to the directory above your workspace, with a name of the form lab07_<rolls>_<branch>_w<NN>.tar.gz.

Take it with you. Upload it to Moodle and also email it to yourself. The lab machines are wiped between sessions, so a bundle left behind is lost.

If you finish early (not marked)

  1. Watch the glider reach the wall. This world has fixed edges, so the glider cannot keep moving forever. Run it for more than the twelve generations e5 allows and print how many cells are alive after each one. It does not die out. At generation 24 it stops changing completely, leaving four live cells in the bottom-right corner. Work out what shape they form.
  2. Find a still life. Those four cells are one: a 2 × 2 block, in which every live cell has exactly the number of neighbours it needs to survive. Add a test to e5 that reports the first generation identical to the one before it, and check that it reports 24.
  3. Make the edges wrap around, so that the cell to the right of column 7 is column 0, and the glider never reaches a wall. This needs one change, inside countNeighbours only. The bounds check you wrote for e3 becomes a calculation instead.

Before you leave

Be ready to answer these two questions out loud. They are the kind of question the viva will ask.

  1. swap(&a, &b) is written with &, but countNeighbours(world, i, j) is not. Why is the array different?
  2. What goes wrong in e4 if you use only one grid instead of two? Which cell is the first to be given a wrong answer, and why?

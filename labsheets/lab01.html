Lab 01: Move-In Day

Electrical Mechanical Metallurgy & Materials
Date Tue Aug 11 Wed Aug 12 Wed Aug 12
Time & Room 2:00–4:00 pm · Lab 4022 2:00–4:00 pm · Lab 4022 2:00–4:00 pm · Lab 4021

Evaluation: not graded — this is the setup lab. But the full machinery (self-check, bundle, submission) runs anyway, at zero stakes: learn the system today, be graded by it from Lab 02.

Teams: one or two students per machine. Pairs: one of you drives (keyboard), the other navigates (owns the sheet, calls the predictions). Swap roles at the half-time whistle. Both of you must be able to explain every command afterwards.

What you’ll be able to do after this lab

Identity & orientation pwd, whoami, hostname, uname, history, clear
Files & navigation ls (-l -a -R), cd, mkdir, touch, cp, mv, rm -i, cat, less, nano
Getting code tar, wget
Toolchain & composition gcc, ./prog, > , |, wc, man, --help, tab-completion
Permissions reading rwx, chmod +x, octal 755 (yes — that’s binary, from this week’s lecture)
Processes Ctrl-C, &, pgrep, kill — the fire extinguisher
System info df -h, du -sh, env, echo $PATH

Pre-lab (at home, ~30 min, strongly recommended)

Play the first four modules of Linux Survival — a simulated terminal, impossible to break. If you want a real one in your browser: Webminal.

One idea before you type anything

The terminal is the course’s third machine. It has a vocabulary of words; it runs the ritual you have already watched twice — read a command → execute it → print → repeat — and it does exactly what you say, never what you mean. Everything you learned from the Turtle applies. Everything.

The map — read this aloud together before typing (5 min)

Everything stored on this computer lives in one big tree. A folder (directory) is a box that can hold files and other boxes; a file is a page inside a box; a path is an address, read from the root / downward:

/                            ← the root: everything starts here
└── home
    └── student              ← the shared home
        └── csp_labs_f26
            └── w02-l01-…    ← YOUR workspace today

And the single most important fact of the day: you are always standing somewhere in this tree. Every command you type acts from where you stand. Three commands are your legs and eyes: pwd (where am I standing?), ls (what can I see from here?), and cd somewhere (walk there; cd .. walks one level up).

When the machine says No such file or directory it means: “from where I’m standing, I can’t see that name.” Do not panic, do not retype harder. Run the compass: 1) pwd — where am I? 2) ls — what’s actually here? 3) cd to the right place, then try again. Nine out of ten errors in this lab are cured by exactly this.

Copying commands. Only the command boxes on this page carry a copy button (top-right of the box) — everything else is for reading, not pasting. And careful: pasting into a terminal is not Ctrl+V — use Ctrl+Shift+V (and Ctrl+Shift+C to copy from the terminal). For short commands, though: type them. Fingers learn what eyes only skim.

Act 0 · Install (10 min)

The lab pack is pre-placed on each machine (ask where). If it isn’t — or you’re at home — fetch it from the course site:

wget https://acads-iit-jammu.github.io/csp-f26-dhavala/labs/lab01.tar.gz

Unpack it and run the installer:

tar xzf lab01.tar.gz
cd lab01
./install.sh

The installer will tell you which branch it thinks you are (it reads the machine’s name and today’s date — ask yourself: how?), ask for your team’s roll number(s), and build your session workspace: /home/student/csp_labs_f26/w02-l01-<branch>-sd. (Practising at home, where that path doesn’t exist? The installer switches to practice mode and creates the workspace right where you ran it — everything else works identically.) This machine is shared and forgets everything — your workspace lives for today only; your work leaves with you at the end (Act 5).

Now walk to your workspace. Do not type any * — your workspace’s exact name depends on your branch, and the installer just printed it for you under “Next steps”. Type the cd line it printed. It will look like this (yours may say ee, me or mt, and can end in -2 if another team used this machine first):

cd /home/student/csp_labs_f26/w02-l01-me-sd

Then the most important step of the day — start the session recorder. Everything you type and see from here on is recorded: your lab’s own machine diary. (To stop it later: type exit.)

script session.txt

Act 1 · Claim the machine (10 min)

Who are you, where are you, on what? Run each of these, predicting the output first. The first answer is a surprise: you are all student — remember that for Act 5.

whoami
hostname
uname -a
df -h .

Now make the machine’s passport — your first redirection: > sends a command’s output into a file instead of the screen, and >> appends instead of overwriting:

whoami > passport.txt
hostname >> passport.txt
uname -a >> passport.txt
df -h . >> passport.txt
cat passport.txt

Act 2 · Build the home (20 min)

Missions, each a mini spec-card: the ENSURES tells you what must be true when you’re done — you build it. Before every ls, say out loud what it will print — then press Enter.

  1. Create a notes/ directory — your lab notebook. Two files will live in it: README.txt (one line saying what lives where in this workspace) and answers.txt, where you’ll write your answers to the think-questions this sheet asks along the way (they’re marked ✍️). Your notebook travels home in your bundle — we read it. ENSURES: cat notes/README.txt prints your line. (Tools: mkdir, nano.)

  2. Build a practice/ tree, from nothing, yourself — you are the one creating every directory and file here. Target shape:

    practice/
├── a/one.txt
├── a/two.txt
└── b/one.txt

    Rules of the game: make the directories (mkdir -p practice/a practice/b), create the first file empty (touch), but the other two files may not be created by touch — one must be born as a copy (cp) and one must arrive by being moved (mv) from somewhere else you made. (So you’ll create a scratch file and move it — that’s the point.) ENSURES: ls -R practice matches the diagram exactly. Predict the output on paper first.

  3. Now remove your practice/ tree — your first rm. Do it the careful way: rm -ri practice, and read every question it asks before answering. rm has no undo, no bin, no mercy. Respect it today, every day. ENSURES: ls no longer shows practice. (notes/ stays — it’s real; practice/ was scaffolding.)

  4. Rescue skills — get stuck on purpose: open man ls, find what -a does, quit (press q). Try ls --help. Press Tab twice after typing pass. These three moves answer 90% of the questions you’d otherwise ask us.

Act 3 · Make it speak (15 min)

Your starter files are already in the workspace (the installer put them there). Open hello.c and put your name inside the quotes (both names, for pairs):

nano hello.c

Then compile it, run it, capture its output into a file, and count that file’s words by piping it through wc:

gcc hello.c -o hello
./hello
./hello > output.txt
cat output.txt | wc -w

You just compiled a real C program — the same printf whose descent you watched, floor by floor, in Week 1. You’ll understand every line by Week 4; today it’s the telescope check.

✍️ Think-question 1, into notes/answers.txt: why the ./ in ./hello? Run echo $PATH and reason it out — ask us at the end if it doesn’t click.

Act 4 · Kill the runaway (10 min)

Week 2’s Toy Computer trapped itself in an infinite ping-pong and could only be Reset. Real machines give you a fire extinguisher. The starter loop.c is a program that never stops on purpose (it runs silently, so your terminal stays calm). Compile it and run it in the foreground — then put it out with extinguisher #1: Ctrl-C:

gcc loop.c -o loop
./loop

Now start it in the background (that’s the &), where Ctrl-C cannot reach it. pgrep loop prints the runaway’s PID — its roll number, just the number:

./loop &
pgrep loop

Kill that number — extinguisher #2 — replacing 12345 with the number your pgrep printed. Then confirm the fire is out: pgrep printing nothing means no such process remains.

kill 12345
pgrep loop

(Curious what pgrep is shorthand for? Run plain ps and find your loop in the crowd — that’s the long way, and on a shared machine it is a crowd.)

Remember this for later: ./loop &, pgrep, and kill <PID> are one-time commands. They must NOT go into your replay.sh in Act 6. That PID number was true for one moment on one machine; replayed later it could kill someone else’s process.

Every programmer writes an infinite loop eventually. Now you’ve already survived one.

Act 5 · Lock up and take your work (15 min)

  1. Look at a permission string: ls -l hello. Decode rwxr-xr-x on paper: three groups of three bits — 111 101 101 = octal 755. This week’s number systems, wearing work clothes.

  2. Try chmod 600 passport.txt, then ls -l passport.txt. ✍️ Think-question 2, into notes/answers.txt: you are all logged in as student — so who exactly did you just lock out? (Honest answer: nobody in this room. chmod guards between users, and this whole room is one user. That is what permissions really are — and why real systems give each person their own account.)

  3. Stop the recorder (type exit — you’ll see “Script done”), then run the self-check:

    ./check.sh

    Red lines tell you what’s missing, never how — that’s your job. bonus-open lines are not required today (they’re Act 6, at home). When the required lines are green — or when time is up; an imperfect bundle beats no bundle — bundle up:

    ./check.sh --bundle

  4. The bundle (../lab01_<rolls>_<branch>_w02.tar.gz) is your work. Copy it out — Moodle upload (link announced in lab), and always also email yourself a copy. Then leave the machine clean: your workspace will be swept automatically before the next lab.

Act 6 · Bonus, at home: your history becomes a program

Do this on any machine — extract the lab pack anywhere and ./install.sh puts a practice workspace right where you run it.

Your recorded history is a log. Turn it into a program:

history > replay.sh
nano replay.sh

Editing rules — read before touching replay.sh:

  1. Every line starts with a number (like 501 ./hello). Those are history bookkeeping, not commands — a replay would try to run a program called 501. Delete every line number.
  2. Make the very first line exactly: #!/bin/sh — it tells the machine which language this program speaks.
  3. KEEP only commands that make sense every time they run: ./hello, cat output.txt | wc -w, ls -l.
  4. DELETE ./loop & — a replay would start a runaway with nobody watching.
  5. DELETE pgrep and kill <PID> — that PID was true for one moment of one afternoon. Replay it tomorrow and you might kill a stranger’s process.
  6. The self-check runs your replay.sh and reports it as a bonus item.

Now run it — before doing anything else:

./replay.sh

Permission denied! This is not an error — it is a lesson. A freshly created file is not allowed to run; you must grant it the execute permission yourself, then run it again:

chmod +x replay.sh
./replay.sh

✍️ Bonus for notes/answers.txt: in one line, what is the difference between a log and a program? (Hint: a log records what happened; a program must be true whenever it runs.) Anything you can do, you can automate — but only the repeatable parts.

Reflect

✍️ Think-question 3, the last line of notes/answers.txt: which single command surprised you most today, and why?

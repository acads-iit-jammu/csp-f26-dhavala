Why Assemblers and Linkers Exist

A .o file is not a broken executable. It is deliberately incomplete — and that is the whole idea.

Deck 08 showed you what the four stages do, one command at a time. These notes answer the harder question: why is it built this way at all? Why not one program that takes source and hands back something that runs?

Because humans, compilers and machines each want a different representation of the same program — and because at each stage, nobody yet knows enough to finish the job.

1. Why we need an assembler

The machine wants raw binary instructions. Humans will not write those. So a symbolic layer was invented:

machine code    10110000 01100001
assembly        MOV AL, 61h          <-- the same instruction

The assembler translates symbolic machine instructions into the actual bytes.

But why is it a separate program? A compiler could emit bytes directly. It emits text instead because that text is a clean interface: one assembler can serve many compilers, and a human can read, check, and hand-tune what came out. You used that interface yesterday — gcc -S is only possible because the boundary exists.

2. Why we need a linker

The linker solves a different problem: programs became too large to write and compile as one file.

main.c    math.c    io.c    sort.c

If every small change required recompiling everything, development would crawl. The solution is to compile each source file independently and join the results later:

main.c -> main.o  \
math.c -> math.o   }--- linker ---> executable
io.c   -> io.o    /

Edit only math.c? Recompile only math.c, then relink. That is separate compilation, and it is why the linker was invented.

3. Object files are deliberately incomplete

Here is the clever part. Suppose main.c says:

int x = add(3, 4);

but add() is defined in another file. When main.c is compiled, the compiler does not need to know where add will finally live in memory. It leaves a note:

CALL add
     ^
     address not known yet
main.o saysmath.o says
undefined symbol: adddefined symbol: add

The linker matches them.

Compile now; decide final addresses later.

This is the U printf you saw in nm hello.o, seen from the other side. The U was never damage. It is a question left open on purpose.

4. Relocation — you can see the note

The compiler does not just leave a vague gap. It records exactly where the hole is and what must fill it:

$ objdump -r main.o

RELOCATION RECORDS FOR [__text]:
OFFSET            TYPE                    VALUE
0000000000000018  ARM64_RELOC_BRANCH26    _add

Read it as a sentence: “at byte 24 of my code there is a branch instruction; when you know where add is, patch it in.” Later the linker discovers add is at 0x401230 and writes that address into the hole. The patching is called relocation.

On the lab's Linux machines the same line reads R_X86_64_PLT32  add — same sentence, different processor.

5. The experiment: when does the error appear?

Do this yourself. It takes two minutes and it settles the question permanently.

/* main.c */
int add(int, int);                 /* a PROMISE, not a definition */

int main(void)
{
    return add(2, 3);
}

Compile without linking:

$ gcc -c main.c
$          <-- it succeeds

Most people expect an error here, because add() does not exist. The compiler is satisfied anyway: it was told int add(int, int); and it trusts that declaration. Now link:

$ gcc main.o -o main
undefined reference to `add'
Its only question
Compiler“Is this valid C, given the declarations I was shown?”
Linker“Can I actually find everything you promised existed?”

Now write the other half and link both:

/* add.c */
int add(int a, int b) { return a + b; }

$ gcc -c add.c
$ gcc main.o add.o -o main       <-- now the linker is satisfied
$ ./main; echo $?
5
The compiler trusted your word. The linker is the one that checks whether you kept it. Knowing which of the two complained is half of debugging — and it is why undefined reference is never a syntax problem.

6. So what does #include actually do?

Two things you have been told, which sound contradictory:

  • #include <stdio.h> pastes the file in — you watched it happen with gcc -E.
  • #include <stdio.h> does not give you printf.

Both are true, and the gap between them is the point.

What stdio.h containsWhat it does not contain
the declaration: int printf(const char *, ...); — printf exists, and this is its shape the implementation — the thousands of lines that actually format and print

So the preprocessor really does paste in a file. That file is a list of promises, not a body of code. The compiler reads the promise and is content; the linker goes looking for whoever keeps it.

Header = the contract. Library = the implementation. This is exactly the GIVEN / ENSURES habit you use on your own programs. C has been doing it to you since Lab 01.

7. Static and dynamic linking

Static linkingDynamic linking
the library's code is copied into your executable your executable records which library to load when it starts
bigger file; self-contained; no surprises at run time smaller file; one libc on disk serves every program on the machine
library updated → you must relink library updated → every program gets the fix
Program A --\
Program B ---+---> libc.so ---> printf
Program C --/
This is why nm hello on the finished executable still showed U printf. Your program was dynamically linked: the linker did not paste printf in — it wrote down where to find it. Run ldd hello (or otool -L hello on a Mac) and you will see the library it intends to ask.

8. The deeper design principle

Delay a decision until it reaches the component that has enough information to make it.

StageKnowsCannot yet know
Compilerwhich instructions are neededthe final addresses
Assemblerhow instructions become byteswhere external functions live
Linkerall the object files at oncewhich machine will run it
Loaderthe actual memory it is given—
C programmer  ->  symbolic program
Compiler      ->  symbolic machine-level intentions
Assembler     ->  machine code with holes and references
Linker        ->  a complete address space
Loader        ->  the program placed in memory and executed

Notice this is not a fact about C. It is an engineering habit: do not force a decision at a point where the information is missing — carry it forward instead. You will meet it again in interfaces, in APIs, and in every system that has to be built by more than one person.

A .o file is not a broken executable. It is deliberately incomplete. That incompleteness is what makes separate compilation, libraries, and modular programming possible at all.

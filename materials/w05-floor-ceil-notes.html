Floor and Ceiling

One sentence of a problem. Two loops. And a correctness argument that fits in five words: L < X < U.

The problem. Given a real number X, find floor(X) (the largest integer not above it) and ceil(X) (the smallest integer not below it). That is the whole statement. It is short enough to hold in your head, and it will take us through loop invariants, two different search strategies, algorithmic cost, and two ways a program can lie to you.

1. The obvious answer is wrong

Just cast it, surely?

(int) 3.7  =  3          <-- looks right
(int)-3.7  = -3          <-- floor(-3.7) is -4

A cast truncates towards zero. For positive numbers that happens to agree with floor; for negative numbers it does not. So a one-line answer that passes every test you would casually try is wrong on half the number line.

This is worth sitting with for a moment. The bug is not in the arithmetic — it is in the specification. "Chop off the decimals" and "the largest integer not above X" are different requirements that agree on the examples you happened to pick. Twenty lines of loop follow from taking the spec seriously.

2. The plan: bracket, then bisect

Two phases, two loops, two different jobs.

PhaseWhat the loop doesStops when
1 — bracketgrows an interval [L, U] until X is trapped inside itL <= X <= U
2 — bisectshrinks the interval, always keeping X insideU - L == 1

And then you are done, with no final calculation at all: if L < X < U and U - L == 1, then L is floor(X) and U is ceil(X). That is what the definitions say.

3. Phase 1: how to search a space with no known size

We are not told how big X might be. So don't guess an upper bound — double until you have one. Starting from [0,1] with X = 100:

L = 1,   U = 2
L = 2,   U = 4
L = 4,   U = 8
L = 8,   U = 16
L = 16,  U = 32
L = 32,  U = 64
L = 64,  U = 128       <-- 100 is inside. Seven steps, not a hundred.

This has a name: exponential search (or galloping search). It is the standard move when the search space is unbounded, and it costs about log₂X steps to find a bound.

4. Phase 2: the invariant is the correctness argument

Now halve the interval, over and over. With X = −3.7 in [-10, 0]:

L = -10, U =  0, mid = -5   mid < X, so L = mid   -> [-5, 0]
L =  -5, U =  0, mid = -3   mid > X, so U = mid   -> [-5,-3]
L =  -5, U = -3, mid = -4   mid < X, so L = mid   -> [-4,-3]
U - L is 1. Stop.           floor = -4,  ceil = -3

At every line above, L < X < U was still true.

That sentence is the loop invariant — the thing the loop is careful never to break. It is not decoration; it is the proof. Because the invariant holds and the interval has shrunk to width 1, the answer follows immediately. Ask this of every loop you write:

What does this loop refuse to break? If you cannot say, you do not yet know whether it is correct — you only know it did not crash on your example.

And the loop must stop: U - L is a positive integer that strictly decreases every pass. A decreasing positive integer cannot go on forever. That is a termination argument, and it is separate from correctness.

5. What does it cost?

The instrumented version counts its own steps. Starting from [0,1]:

Xexpansionsshrinkstotal steps
3.7213
1 000.510919
1 000 000.5201939
1 000 000 000.5302959

Read the table before reading the next sentence. X grows a thousandfold each row. The cost grows by twenty steps. Not a thousandfold. Not double. A fixed amount, every time you multiply the input.

That is what logarithmic means — here about 2 × log₂X steps. A number with a hundred digits would cost roughly 660 steps. This is the entire reason anyone cares about binary search, and you can see it in four rows of a table without knowing the word.

One more thing the table shows: for an integer X the shrink phase exits early, because mid == X is spotted before the interval is narrow. Same algorithm, different cost, depending on the input. That is the difference between best case and worst case.

6. Breaking it on purpose

Try X = 1e19 — just past the largest long long, 9223372036854775807. Watch the expansion loop:

L = 2882303761517117440,  U = 5764607523034234880
L = 5764607523034234880,  U = -6917529027641081856   <-- ??
L = -6917529027641081856, U = 4611686018427387904
L = 4611686018427387904,  U = -9223372036854775808
L = -9223372036854775808, U = 0
L = 0,                    U = 0                      <-- forever

W = 2 * W overflowed. U wrapped round to a huge negative number, everything collapsed to zero, and the loop condition X > U became permanently true. The program never stops.

Two lessons collide here. Week 3's: overflow is silent — nothing warned you. Week 5's: a loop whose guard can never become false is the most expensive bug you can write, because it does not fail, it just never finishes.

The fix is three lines, and it goes before the doubling, not after:

if (W > LLONG_MAX / 2 || U > LLONG_MAX - W) {
    printf("STOP: X is too large in magnitude for long long.\n");
    return 2;
}
Notice the shape of that check: the loop may only take a step if the step is representable. It is a precondition on the loop body. And an honest error message is a result — a hang is not.

7. One surprise that is not the algorithm's fault

Enter X: 9007199254740993        (that is 2^53 + 1)
floor(X) = 9007199254740992
ceil(X)  = 9007199254740992

Off by one, and the loop is blameless. A double has 53 bits of significand, so beyond 2⁵³ it cannot represent every integer. scanf rounded your number on the way in; the program then computed the exactly correct floor of the number it actually received.

Week 2 is still collecting debts. It also means the phrase "X is exactly an integer" is doing something subtler than it looks.

8. Four things to take away

  • Read the specification, not the examples. The cast agrees with floor on every positive number you would casually test.
  • Name your invariant. L < X < U is not a comment; it is the reason the program is right.
  • Correctness and termination are two separate arguments. The invariant gives the first; a strictly decreasing positive integer gives the second.
  • Cost is measurable, not a feeling. Count the steps, tabulate, and the shape of the growth tells you which class of algorithm you wrote.

9. Try it yourself

  • Rewrite Phase 2 as a do-while. Does anything break for X = 0.5 in [0,1], where the loop should not run at all?
  • The integer case is handled in three different places in the program. Can you make it one? Should you?
  • Add a counter to Phase 2 and find an X that maximises the shrink steps for a fixed starting interval. What kind of number is it?
  • What happens for L = -5, U = 5, X = 0? Predict before running.

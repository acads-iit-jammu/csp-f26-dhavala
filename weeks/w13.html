Application: storing sensor readings

A temperature sensor sends readings to a program. If the number of readings is known in advance and remains fixed, an array of that size is suitable. For example, int readings[100]; can store 100 readings.

If the recording continues beyond 100 readings, this array cannot be enlarged. The program needs more storage while retaining the readings already collected. Dynamic memory allocation allows the program to request storage at runtime and resize it as more readings arrive. Resizing may move the data to a new location.

After collecting the readings, the program may need to find the maximum. One recursive approach finds the maximum of the first n - 1 readings and compares it with the last reading. The lectures cover allocation first, followed by recursive functions.

Lecture overview

Monday, 26 October — Dynamic memory allocation

Learning goal: allocate storage, initialise it, pass it to a function, resize it safely and release it once. Distinguish the lifetime of a pointer from the lifetime of the object it refers to. Dynamic allocation gives control over storage size and lifetime; it is not the only way C can express a runtime-sized array.

Teaching sequence Supporting artifact
Start with the need: a fixed array is full, or a result must outlive the function that creates it. Compare storage choices. Then start the allocation trace; distinguish a pointer from its allocation.
malloc, sizeof *p, failure checking, initialisation, array access and free. Step through allocate → write → release; compare calloc.
Resize a populated array. Preserve the old pointer if realloc fails. Run both resize scenarios; explain which values survive.
Aliases, dangling pointers, double-free and losing the last pointer. Connect to arrays of structures. Alias and leak scenarios; students explain before advancing.
Exit check: repair an allocation/cleanup fragment and explain ownership. Revisit one scenario without its explanation.

Open the memory explorer: Who owns this memory?

The explorer is a conceptual trace, not a live allocator. Released storage is never read to demonstrate a bug. Addresses are symbolic; failed allocation is a selectable scenario. The longer string-copy example and further allocation exercises belong in reading/lab practice.

Tuesday, 27 October — Recursion

Learning goal: identify the base case, explain progress towards it, and trace the work done after a recursive call returns. Each invocation has its own parameters and locals; an array argument still refers to the caller’s data.

Teaching sequence Supporting artifact
Derive factorial from the smaller problem; include 0!. Predict fact(3) before running the trace.
Descend into calls, pause the caller, then unwind the returns. Step through the stack; identify each pending multiplication.
Find the largest element in an array recursively. Pass Monday’s allocated array without copying it. Maximum trace, including the singleton base case.
Virahanka/Fibonacci: two smaller problems and repeated work. Compare call counts for small inputs.
Diagnose a missing base case, non-shrinking input and a missing return; exit prediction. Reset a trace and ask students to explain the next state.

Open the recursion explorer: Where does a recursive call return?

The explorer uses small inputs and shows logical call frames. It does not imply that recursion is always faster or that compilers must use this exact physical stack layout. Binomial coefficients, balanced recursive maximum and recursive binary search are reading extensions. See also the Tuesday PAGAL discussion.

Monday notes: allocating and owning memory

When dynamic allocation is needed

Consider the sensor application. The program initially has room for 100 readings. After 100 readings have been stored, another reading arrives. Writing it to readings[100] would be out of bounds. Changing a variable that holds the count does not change the array’s capacity.

One solution is to create a larger array, copy the existing readings into it and continue recording. Dynamically allocated storage provides a resizing operation, realloc, for this purpose. It can enlarge the existing allocation or move the data to a larger allocation. The program does not need to copy the readings itself. It must check whether resizing succeeded and use the returned pointer.

Dynamic allocation also supports two related requirements:

  • A size determined at runtime. The program reads the number of records from a file and allocates space for that number.
  • Data needed after a function returns. A function allocates and fills an array, then returns its pointer to the caller. The caller uses the array and later releases it. Returning a pointer to an ordinary local array would be invalid because that array ceases to exist when the function returns.

Alternatively, the caller can provide an array and pass its capacity to the function. This is suitable when the caller can determine the required capacity.

Storage choice What it can do What it cannot do
Ordinary local array, e.g. int a[100]; Hold up to its fixed capacity during the block’s execution Grow that array object or keep it alive after leaving its block
Variable-length local array, e.g. int a[n];, where supported Choose its size when its declaration executes Resize the existing array or extend its lifetime past its scope; support is optional in C11
Static array Keep storage for the duration of the program Grow its fixed capacity or automatically give each function call an independent result
Dynamically allocated storage Choose a size at runtime, resize storage and control when it is released Guarantee allocation success, unlimited memory or automatic cleanup

A variable-length array can also use a size determined at runtime, where supported. Its size cannot subsequently change, and its lifetime ends on leaving its scope. Dynamic allocation is useful when these restrictions do not suit the application.

Allocation functions

malloc and calloc allocate storage. realloc resizes an allocation. free releases it. These functions are declared in <stdlib.h>.

Need Choose Reason
Store values that will all be assigned before use malloc No initial values are requested; write the elements before reading them
Start an integer counter array at zero calloc Zeroed bytes give these integer elements their required initial zero values
Change the capacity while retaining existing contents realloc Preserves contents up to the smaller of the old and new sizes on success
Finish using an allocation free Releases that storage for reuse

The length is the number of readings stored. The capacity is the number that can fit. For example, after enlarging a full array from 100 to 200 elements, the length is still 100. The added elements must be assigned values before use.

Appropriate, inefficient and incorrect uses

Situation Appropriate use Correct but potentially wasteful Incorrect use
Read n values, assigning every element malloc, check, then fill calloc when every zero will immediately be overwritten; its zero-initialisation is unnecessary for this algorithm Read an element from malloc storage before assigning it
Start n integer counters calloc, check, then increment calloc followed by another loop assigning zero Use uninitialised malloc elements as counters; malloc plus an explicit zeroing loop is valid
Append many values Grow capacity in chunks, then fill the added elements Call realloc for every single append; repeated moves can repeatedly copy old data Write past capacity, or assume the added elements are already zero
Resize an existing allocation Keep the old pointer until a temporary result has been checked Allocate a new block, copy and free the old one manually when realloc suffices Overwrite the only pointer with a failed realloc result, losing access to the old allocation
Repeat a calculation with the same buffer size Reuse the buffer while it is needed; free it at the end Allocate and free a replacement buffer on every iteration without a need for separate storage Keep overwriting the last owning pointer without freeing its previous allocation
Finish using shared storage Free once after its last use; stop using every alias Keep an unnecessarily large allocation alive until much later Free twice, access freed storage, or treat p = NULL as a substitute for free(p)

For repeated appends, increasing capacity from 100 to 200, then to 400, reduces the number of resize requests. It also reserves space that may remain unused. Resizing by one element each time may require repeated copying. Actual allocation costs depend on the implementation. calloc is not necessarily slower than malloc; its zero-initialisation is unnecessary when every element will be immediately overwritten.

Runnable examples

The structure and string examples are follow-up reading. Every complete program below is independent: copy one into example.c, compile, and run it. No keyboard input is needed; change the initial values to experiment. Syntax summaries are reference fragments, not complete programs.

cc -std=c11 -Wall -Wextra -Wpedantic example.c -o example
./example

malloc: reserve storage, then initialise it

Use malloc when the program will assign each element before reading it. The example allocates three integers, assigns their values and computes their sum. The count is fixed here so the output is reproducible; the same expression can use a validated count read at runtime.

Definition and syntax: malloc(bytes) from <stdlib.h> reserves the requested number of bytes and returns a pointer to them, or NULL on failure. For an array of n elements, use int *p = malloc(n * sizeof *p);. sizeof *p is the size of one pointed-to element; for this int expression it does not dereference p at runtime. C does not require a cast of the returned pointer.

Initialisation: the pointer receives the returned address; the elements remain uninitialised. Check p, then assign each element before reading it.

Usage: p[i] accesses element i, just as with an array. Pass both the pointer and the element count to functions; a pointer does not remember the array length.

Cautions: indices must be from 0 to n - 1. For a count obtained from input, validate that it is positive and that n * sizeof *p fits in size_t before allocating. For example, with a validated size_t n, reject n > SIZE_MAX / sizeof *p (SIZE_MAX is provided by <stdint.h>). The examples here use fixed small positive counts. sizeof p is the size of the pointer, not the allocated array.

Complete program — allocate, initialise, pass to a function, release:

#include <stdio.h>
#include <stdlib.h>

int sum(const int a[], int n)
{
    int total = 0;
    for (int i = 0; i < n; i++) {
        total += a[i];
    }
    return total;
}

int main(void)
{
    int n = 3;
    int *p = malloc(n * sizeof *p);
    if (p == NULL) {
        fprintf(stderr, "Allocation failed\n");
        return 1;
    }
    for (int i = 0; i < n; i++) {
        p[i] = (i + 1) * 10;
    }
    printf("Sum = %d\n", sum(p, n));
    free(p);
    p = NULL;
    return 0;
}

Expected output on allocation success:

Sum = 60

calloc: reserve storage with zeroed bytes

Suppose the program counts readings in three temperature ranges. Each counter must start at zero. calloc provides zero-initialised integer storage. malloc followed by a loop assigning zero is also valid.

Definition and syntax: calloc(count, element_size) allocates storage for count elements and sets all its bytes to zero. Use int *p = calloc(n, sizeof *p); and check for NULL.

Initialisation and usage: for an integer array, these zeroed bytes represent integer zero. Read or update its elements using p[i]; release it with free.

Cautions: do not generalise this to portable initialisation of every possible C type: all-bits-zero is not guaranteed to represent a null pointer or every floating-point zero. calloc still can fail and still needs cleanup.

Complete program:

#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *counts = calloc(3, sizeof *counts);
    if (counts == NULL) {
        fprintf(stderr, "Allocation failed\n");
        return 1;
    }
    printf("Initially: %d %d %d\n", counts[0], counts[1], counts[2]);
    counts[1]++;
    printf("After update: %d %d %d\n", counts[0], counts[1], counts[2]);
    free(counts);
    return 0;
}

Expected output on allocation success:

Initially: 0 0 0
After update: 0 1 0

realloc: change the allocation size

The example starts with two stored readings and increases capacity to four. realloc preserves the two existing values on success. The program then assigns values to the two added elements.

Definition and syntax: realloc(p, new_bytes) attempts to resize an existing allocation. Use a temporary pointer: int *tmp = realloc(p, new_n * sizeof *p);. For a positive new size, failure returns NULL and leaves the original allocation valid. Success preserves the contents up to the smaller of the old and new sizes.

Initialisation and usage: check tmp first, then assign p = tmp on success. Initialise any added elements before reading them. The allocation can move.

Cautions: direct assignment p = realloc(p, ...) can lose the only pointer to the original allocation on failure. After success, use the returned pointer; previous aliases into the old allocation must no longer be used, even if the returned address happens to be unchanged. Avoid zero-size requests: use free when the intended action is to release storage.

Complete program:

#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *p = malloc(2 * sizeof *p);
    if (p == NULL) {
        fprintf(stderr, "Allocation failed\n");
        return 1;
    }
    p[0] = 7;
    p[1] = 2;

    int *tmp = realloc(p, 4 * sizeof *p);
    if (tmp == NULL) {
        /* p is still valid. This program chooses to clean up and exit. */
        fprintf(stderr, "Resize failed\n");
        free(p);
        return 1;
    }
    p = tmp;
    p[2] = 5;
    p[3] = 8;
    printf("Values: %d %d %d %d\n", p[0], p[1], p[2], p[3]);
    free(p);
    return 0;
}

Expected output on allocation success:

Values: 7 2 5 8

free, aliases and ownership

Once the program no longer needs the readings, it releases their storage with free. The allocation remains in use until it is released, even if the pointer that originally held its address goes out of scope. If two pointers refer to the same allocation, it must still be freed only once.

Definition and syntax: free(p) releases an allocation. It does not delete the pointer variable or assign NULL to it. free(NULL) is permitted.

Initialisation and usage: initialise a pointer to NULL when it does not yet refer to an object. Decide which part of the program is responsible for releasing an allocation; this is its owner. int *q = p; copies the pointer, not the array.

Cautions: release an allocation exactly once, using its starting pointer from an allocation function. Do not free a local array, p + 1, or already freed storage. Do not dereference, print or compare a stale pointer value after release. Assigning p = NULL does not fix other aliases. Assigning NULL without first releasing the last reachable allocation causes a leak.

Complete program — two pointers, one allocation:

#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *p = malloc(sizeof *p);
    if (p == NULL) {
        fprintf(stderr, "Allocation failed\n");
        return 1;
    }
    *p = 7;
    int *q = p;
    *q = 9;
    printf("Through p: %d; through q: %d\n", *p, *q);
    free(p);             /* Release the shared allocation once. */
    p = NULL;
    q = NULL;            /* Overwrite the stale alias; do not read it. */
    printf("Both pointers reset\n");
    return 0;
}

Expected output on allocation success:

Through p: 9; through q: 9
Both pointers reset

Follow-up: dynamically allocated structures and strings

A record array can use dynamically allocated storage in the same way as an integer array. A string requires space for its characters and terminating null character. The example creates an independent string copy, then changes the original string.

Definition and syntax: struct Point *p = malloc(n * sizeof *p); allocates an array of structures. Access an element’s field with p[i].x; p->x means (*p).x, the field of the first pointed-to structure.

Initialisation and usage: assign the fields before reading them. A dynamically allocated string needs room for its characters and the terminating '\0': char *copy = malloc(strlen(source) + 1);. After checking, strcpy(copy, source) copies the characters and terminator; both string functions require <string.h>.

Cautions: char *copy = source only copies an address. Allocating a structure with a pointer member does not allocate storage for that member’s target. Likewise, freeing the structure does not automatically free separately allocated targets. Here source is a valid, terminated, fixed-size string and the destination is large enough; strcpy itself does not check bounds.

Complete program:

#include <stdio.h>
#include <stdlib.h>
#include <string.h>

struct Point {
    int x;
    int y;
};

int main(void)
{
    struct Point *points = malloc(2 * sizeof *points);
    if (points == NULL) {
        fprintf(stderr, "Allocation failed\n");
        return 1;
    }
    points[0].x = 1;
    points[0].y = 2;
    points[1].x = 3;
    points[1].y = 4;

    char source[] = "lab";
    char *copy = malloc(strlen(source) + 1);
    if (copy == NULL) {
        free(points);
        fprintf(stderr, "Allocation failed\n");
        return 1;
    }
    strcpy(copy, source);
    source[0] = 'L';
    printf("First point: (%d, %d)\n", points->x, points->y);
    printf("Second point: (%d, %d)\n", points[1].x, points[1].y);
    printf("Source: %s; independent copy: %s\n", source, copy);
    free(copy);
    free(points);
    return 0;
}

Expected output on allocation success:

First point: (1, 2)
Second point: (3, 4)

Tuesday notes: recursion

When recursion is useful

Consider finding the maximum of the stored readings. For one reading, that reading is the maximum. For n readings, compare the last reading with the maximum of the first n - 1 readings. A function can perform this calculation by calling itself with n - 1 and using the returned value.

This is a recursive solution. It has three parts:

  1. Base case: return the sole reading when n == 1.
  2. Recursive call: find the maximum for n - 1 readings.
  3. Result: compare the returned maximum with the last reading and return the larger value.

A loop can also find the maximum and uses less extra storage than this recursive version. Recursion is useful when describing a problem through smaller instances makes its implementation easier to follow. Its cost depends on the number of calls, the maximum call depth and any repeated calculations.

Task Implementation choice Limitation or error to avoid
Scan an array or compute a running sum A loop is usually sufficient A recursive scan adds call depth proportional to the array length
Solve a problem using smaller instances of itself Use recursion with a base case and a decreasing problem size A missing base case or unchanged argument can prevent termination
Compute Fibonacci values A loop can retain the preceding two values Direct recursion repeatedly computes the same subproblems
Use a recursive answer in the caller Store or return the function’s result Printing the result does not return it to the caller

Recursive functions: base case, smaller problem, return

Definition and syntax: a recursive function calls itself. It uses ordinary C function syntax: return_type name(parameters) { /* body */ }. Place its definition before the first call, or provide a matching prototype. Each call has its own parameters and automatic local variables.

Initialisation: give the first call a valid starting argument. Every execution path must either reach a base case or move towards one. Initialise local values before using them; a local variable in one invocation is not the same variable as one in another invocation.

Usage: describe the answer in terms of a smaller instance, then combine that answer with the work left in the caller. return passes a result to the caller; printing a result does not return it.

Cautions: a base case that is never reached does not stop recursion. Inputs must move towards it. Non-void functions must return a value on every reachable path. Deep recursion can exhaust execution resources; recursion is not automatically faster or more memory-efficient than a loop.

Factorial: one recursive call and pending multiplication

For 5!, the recursive call computes 4!. The caller then multiplies that result by 5. This example shows how execution resumes after a recursive call returns.

Definition: for nonnegative integers, (0! = 1) and (n! = n(n-1)!) for (n > 0). Call syntax: factorial(n).

Initialisation and usage: start with n in 0..12 in this example. The base case returns 1; each waiting caller multiplies the returned answer by its own n. We use unsigned long, which can represent all these results on conforming C implementations.

Cautions: a negative input moves away from the base case in this implementation. Large factorials exceed the integer type’s range; unsigned arithmetic wrapping is not a correct factorial result. The input bound is part of this function’s contract.

Complete program:

#include <stdio.h>

/* Precondition: 0 <= n && n <= 12. */
unsigned long factorial(int n)
{
    if (n == 0) {
        return 1;
    }
    unsigned long smaller = factorial(n - 1);
    return (unsigned long)n * smaller;
}

int main(void)
{
    int n = 5;
    if (n < 0 || n > 12) {
        fprintf(stderr, "Use n from 0 to 12\n");
        return 1;
    }
    printf("%d! = %lu\n", n, factorial(n));
    printf("0! = %lu\n", factorial(0));
    return 0;
}

Expected output:

5! = 120
0! = 1

For factorial(3), calls descend through 3, 2, 1, 0. Returns carry 1, 1, 2, 6 back up. The multiplication happens after the smaller call returns.

Recursive maximum: an array and its current length

To find the largest reading, first find the maximum of the first n - 1 readings. Then compare that result with the last reading. The recursive calls use the same array; they do not copy it.

Definition: the maximum of one element is that element. For a longer array, compare the last element with the maximum of the preceding elements. Call syntax: largest(a, n), where n >= 1 and a points to at least n initialised integers.

Initialisation and usage: start with the full length. Each recursive call uses n - 1. maxOfPrefix holds the maximum of the first n - 1 elements. The array elements are shared between calls; passing an array does not copy them. const prevents this function from modifying elements through a.

Cautions: an empty array has no maximum under this contract. Do not use zero as the base answer: that fails for all-negative data. This version makes n calls and has linear recursion depth; a loop avoids that depth.

Complete program — connect recursion to Monday’s allocation:

#include <stdio.h>
#include <stdlib.h>

/* Precondition: n >= 1; a points to at least n initialised ints. */
int largest(const int a[], int n)
{
    if (n == 1) {
        return a[0];
    }
    int maxOfPrefix = largest(a, n - 1);
    if (a[n - 1] > maxOfPrefix) {
        return a[n - 1];
    }
    return maxOfPrefix;
}

int main(void)
{
    int n = 4;
    int *a = malloc(n * sizeof *a);
    if (a == NULL) {
        fprintf(stderr, "Allocation failed\n");
        return 1;
    }
    a[0] = -4;
    a[1] = -2;
    a[2] = -9;
    a[3] = -1;
    printf("Maximum = %d\n", largest(a, n));
    printf("Singleton maximum = %d\n", largest(a, 1));
    free(a);
    return 0;
}

Expected output on allocation success:

Maximum = -1
Singleton maximum = -4

Virahanka/Fibonacci: two recursive calls and repeated work

Each Fibonacci value depends on two preceding values. A direct recursive implementation computes both, but may recompute the same value in several calls.

Definition: using the indexing here, (F(0)=0), (F(1)=1), and (F(n)=F(n-1)+F(n-2)) for (n). Call syntax: fib(n).

Initialisation and usage: begin with a nonnegative n; this demonstration limits it to 0..10. Store each smaller answer, then add them. The two separate statements make the order of the calls explicit.

Cautions: fib(5) computes fib(3) more than once. Repeated subproblems make this direct version expensive as n grows; a loop can compute the sequence with linear work and constant extra storage. Large results also overflow. A branching call tree does not mean that all its calls are active simultaneously: one branch returns before the next statement starts the other.

Complete program:

#include <stdio.h>

/* Precondition for this demonstration: 0 <= n && n <= 10. */
int fib(int n)
{
    if (n <= 1) {
        return n;
    }
    int left = fib(n - 1);
    int right = fib(n - 2);
    return left + right;
}

int main(void)
{
    int n = 6;
    if (n < 0 || n > 10) {
        fprintf(stderr, "Use n from 0 to 10\n");
        return 1;
    }
    printf("F(%d) = %d\n", n, fib(n));
    printf("F(0) = %d; F(1) = %d\n", fib(0), fib(1));
    return 0;
}

Expected output:

F(6) = 8
F(0) = 0; F(1) = 1

The argument of the entire summit was that this work is moving to places like Jammu — and that the binding constraint is not real estate or policy or bandwidth. It is whether there are enough people here who can do the work.

That is an unusually direct thing for a first-year programming class to be told. The question of whether such a centre opens in this city, and whether it does serious engineering when it does, is partly a question about the people sitting in this room.

What the industry leaders actually emphasised.

The programme is on the website; the emphasis is not. What came back from those panels was consistent, and it was not about any particular technology.

Continuous learning, as a condition of the job rather than a virtue. Not “keep learning” as a motivational poster. The stronger claim: that the specific tools you are hired for will be substantially replaced during your employment, so the only durable qualification is the demonstrated ability to pick up the next thing quickly. What you know is a depreciating asset. How fast you learn is not.

Compressing onboarding. This one is measurable, which is why industry cares about it. How long before a new engineer can safely change something? It used to be months. The pressure now is to make it weeks. And notice what that is actually a demand for: it is a demand that you can be dropped into a large unfamiliar codebase and become useful quickly. That is precisely the skill last week’s column was about, and which Google now runs an interview round on. Two completely different institutions — a hiring process in California, a talent panel in Jagti — arriving at the same requirement in the same month.

Judgement early, not after a decade. The expectation voiced repeatedly was that juniors will move from producing work to judging work far sooner than before, because the production is increasingly done by AI. The junior role is shifting from “write this” to “decide whether this is right, and whether it is the right thing.”

If that sounds familiar, it should. Week 1 of this course drew it as Specify → Express → Verify and claimed the machine was taking the middle step. That was our argument. It is now also the argument of a room full of people who hire engineers. We did not get that from them and they did not get it from us; it is simply what the situation looks like from both ends.

The part that was not about skills at all.

Here is what genuinely stood out. In a summit about technology, investment and AI, the talent discussion kept returning to things that are not skills: grit, trustworthiness, ownership, the willingness to say you do not know.

That is easy to dismiss as the soft part of a corporate panel. It is worth taking seriously instead, because there is a reason it is getting more weight rather than less.

When producing code was the bottleneck, you could measure someone by output. That measurement is now broken: anyone can produce plausible output. So what remains to evaluate a person on? Whether their work can be relied upon. Whether they say “I checked this” only when they checked it. Whether they stay with a hard problem past the point where it stops being interesting. Whether, when they do not understand something, they say so instead of shipping it and hoping.

The skill landscape moves every few years. These do not. They are also, inconveniently, the ones you cannot acquire the night before.

Which brings us, honestly, to malloc and free.

This is not a stretch, and it is why this column sits in this particular week.

free is a promise that nobody checks. If you forget it, your program still compiles. It still produces the right answer. It passes the tests. It passes code review, most of the time. The leak shows up weeks later as a service that degrades overnight, and by then it is somebody else’s night.

There is no compiler error for a broken promise. C gives you the memory because you asked, and it believes you when you imply you will give it back. The language has no opinion about whether you do. Nothing in this course so far has worked that way: a missing semicolon is caught instantly, a wrong answer is caught by the grader. A leak is the first thing you will write that is wrong in a way that only hurts someone who is not you, and only later.

Now separate two things the word trustworthy is doing, because they are not the same and the connection between them is the whole point.

What it means
A trustworthy work product the program does what it claims, including the parts nobody inspected — it frees what it allocated, it handles the file that would not open
A trustworthy person colleagues can rely on what you hand them and on what you say about it, without re-checking everything themselves

free is the first kind. That is a fact about your code.

The panellists in Jagti were arguing about the second kind. That is a claim about a person, and it is the one being hired for — because, as above, output is no longer evidence of anything.

The connection runs one way, and it is worth being exact about the direction. Nobody becomes trustworthy by resolving to be trustworthy. You become trustworthy by producing trustworthy work, enough times, that people stop needing to verify it. The trait is the accumulated residue of the artefacts. It is built out of instances — this free that you did not skip, this edge case you checked before claiming it worked, this time you said “I am not sure” when the easier thing was to say nothing.

Which is why a memory leak is a slightly larger matter than it appears. It is not a character flaw; it is a bug. But the habit that prevents it — finishing the part nobody will inspect — is the same habit that, repeated for a few years, is what people mean when they call someone reliable. You do not get to build that later. You are building it now, or not, in whichever way you handle the free that nobody is going to check.

Recursion, on Tuesday, asks something related. To write a recursive function you must trust the call you are making — assume it returns the right answer for the smaller problem — while remaining entirely responsible for the base case and for making progress towards it. Trust the part you delegate; own the part that makes it terminate. That is also, more or less, a description of working with an AI.

What to do about it, concretely.

The summit’s message to this region was that the work is coming here if the people are here. Three things follow, none of them dramatic:

  1. Get fast at reading code you did not write. It is the measurable thing industry is now optimising for, under the name “onboarding.” The drills are practice at it.
  2. Protect the ability to judge. Use every tool you like — but stay able to say why an answer is right, because that is the part being hired for.
  3. Build the trait out of the artefacts. free what you malloc. Say when you do not know. Finish the hard one. Each is a small piece of work that holds up unobserved, and that is the only material the reputation is ever made of.

The third is the one that will feel least like computer science and will matter longest.

Tuesday, 27 October: Even the arithmetic underneath AI needs debugging

Remember the Pentium division bug: Thomas Nicely noticed that a trusted processor gave inconsistent answers. Remember Java’s binary-search bug: (low + high) / 2 could overflow before the division happened. A mathematically sensible expression failed on a machine with finite integers. Humans investigated both. Joshua Bloch’s account

Now consider softmax, which converts scores into probabilities inside many AI systems. Barron and colleagues describe two numerical bugs in standard softmax and cross-entropy implementations. Subtracting the largest input already guards against exponential overflow, but rounding can still erase a small learning signal. Another failure produces a non-zero learning signal even when a student model’s scores exactly match its teacher’s. Paper and demonstration

Here is the numerical trap in miniature. For a tiny positive \(u\),

\[ \frac{1}{1+u}-1 = -\frac{u}{1+u}. \]

On paper, they are equal. On a computer, 1 + u may round to exactly 1. The first expression then becomes zero; the second can preserve the small negative value.

This is loss of precision, occurring before \(u\) itself becomes too small to represent. Overflow exceeds the available range; underflow concerns values near the bottom of that range. Avoiding those extremes does not guarantee accurate arithmetic. The paper’s fixes rearrange computations to preserve information that the usual formulas discard. Technical explanation

The reported Gemini assistance adds a striking possibility: AI helping humans repair the numerical machinery used to train AI. That attribution remains unverified here: the paper does not mention Gemini, and we could not independently verify the details in the linked discussion. The collaboration we should aim for is clear: ask the model to challenge an implementation, propose counterexamples and compare alternative formulas. Then reproduce the failure and test the proposed repair.

For a first-year programmer, this is why representation, precision and boundary cases matter. They reach all the way from your C exercises to modern AI. You need enough understanding to recognise a useful diagnosis—and enough discipline to demand evidence before shipping the fix.

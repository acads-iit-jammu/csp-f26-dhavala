Monday — how does the calculator do it?

1 · A question you have never asked

You press √ on a calculator and a number appears. Where does it come from? Nobody stored a table; nobody looked it up. Something computed it — with a loop, a comparison, and nothing you have not already met.

Monday’s lecture answered that conceptually — what a function is, what sin and sqrt are really doing behind the name, and why both come down to the same move: ask a question you can answer, over and over, until the answer is good enough.

These notes are where that becomes code. Nothing below was typed in the lecture, so work through it here: §2–§5 build a function, §6 and §9 build sqrt out of halving, and the two Going Further sections at the end take sin and sqrt all the way down to what the library actually does.

2 · A function is a promise

#include <stdio.h>

int largest(int a, int b);            /* the promise: name, what goes in, what comes out */

int main(void) {
    int x = 7, y = 12;
    printf("largest(%d, %d) = %d\n", x, y, largest(x, y));
    printf("largest(%d, %d) = %d\n", 4, 4, largest(4, 4));
    return 0;
}

int largest(int a, int b) {           /* the keeping of it */
    if (a > b) return a;
    return b;
}
largest(7, 12) = 12
largest(4, 4) = 4
int largest(int a, int b); the declaration — a promise made before it is kept
int largest(int a, int b) { ... } the definition — the keeping of it
largest(x, y) the call

The declaration is what lets main use largest before it has been written. C reads your file top to bottom and will not take your word for a name it has not met.

3 · Scope — a function’s variables are its own

#include <stdio.h>

int twice(int n) {
    int result = n * 2;          /* result belongs to twice, and to nobody else */
    return result;
}

int main(void) {
    int n = 5;                   /* a DIFFERENT n, living in main */
    printf("main's n before : %d\n", n);
    printf("twice(n)        : %d\n", twice(n));
    printf("main's n after  : %d\n", n);
    /* printf("%d", result);     <-- would not compile: result is not ours */
    return 0;
}
main's n before : 5
twice(n)        : 10
main's n after  : 5

Uncomment that last line and the compiler stops you:

scope.c:13:18: error: use of undeclared identifier 'result'
   13 |     printf("%d", result);
      |                  ^~~~~~

result lived inside twice. Outside it, the name does not exist. And main has its own n while twice has its own n — different variables that happen to share a name.

Everything in §4 follows from this section. It is not a separate rule.

4 · Call by value

void addOne(int n) { n = n + 1; }

The parameter n is a local variable of addOne, started off as a copy of whatever you passed. Changing it changes addOne’s n. The caller’s variable never hears about it — not because of a rule about arguments, but because of §3.

5 · Call by reference

void addOne(int n)   { n = n + 1; }        /* gets a COPY */
void reallyAddOne(int *n) { *n = *n + 1; } /* gets WHERE the value lives */
after addOne(count)        count = 10
after reallyAddOne(&count) count = 11

&count is where count lives. int *n is a parameter that receives such a place, and *n reaches through it to the value.

You have been doing this since Week 3. scanf("%d", &count) needs the & for exactly this reason: scanf cannot hand a value back through a copy, so you tell it where to put it.

When to use which. By value to read something. By reference when the caller’s variable must change — or when one return is not enough, which is §7.

6 · Square root, by halving

√5 is somewhere between 0 and 5. Guess the middle: 2.5. But 2.5 × 2.5 = 6.25, too big — so the answer lies in [0, 2.5]. Halve again. Each step throws away half of what is left.

This is bisection, and it is the method we talked through in class. It is not the fastest way to a square root — And What sqrt(x) Does shows the one that is, and measures the difference: 41 halvings against 6 steps for the same answer.

7 · Two answers out of one function

double mySqrt(double x, int *halvings) {
    double lo = 0.0, hi = x;
    if (x < 1.0) hi = 1.0;
    int k = 0;
    while (hi - lo > 1e-12) {
        double mid = (lo + hi) / 2.0;
        if (mid * mid > x) hi = mid;
        else               lo = mid;
        k++;
    }
    *halvings = k;              /* the SECOND answer, sent home by reference */
    return lo;                  /* the first answer, returned normally */
}
sqrt(5) = 2.2360679775, found in 43 halvings

The root comes back as the return value. The number of halvings comes back by reference. That is when you reach for a pointer — not to be clever, but because one return is not enough.

8 · Look at what you actually wrote

Nothing in that loop knows the words “square root”. It knows only one thing: is my guess too big? And “too big” means mid*mid - 5 > 0 — the sign of a function.

You did not write sqrt. You wrote find where a function crosses zero, and then used it on one particular function.

9 · Change f, solve something else

This is the step that matters, and it is the one the lecture spent longest on: once the method is separate from the problem, changing the problem costs one line.

double f(double x) { return x*x - 5.0; }      /* zero at sqrt(5) */
  root = 2.2360679775   in 43 halvings
  check: sqrt(5)  = 2.2360679775
double f(double x) { return x*x*x - 5.0; }    /* zero at the CUBE root */
  root = 1.7099759467   in 43 halvings
  check: cbrt(5)  = 1.7099759467
double f(double x) { return cos(x) - x; }     /* where does cos x equal x? */
  root = 0.7390851332   in 43 halvings
  check: cos(r)   = 0.7390851332  vs r = 0.7390851332

One thing has to change before that works, and it is worth seeing why. §7’s test was if (mid*mid > x) — it assumed the quantity grows as the guess grows. That is true of x² − 5 and of x³ − 5. It is false of cos x − x, which falls through zero. Ask that version for the third root and it walks the wrong way and returns 5.

So the general form does not ask “is it too big?” but “which half contains the crossing?”:

double bisect(double lo, double hi, int *halvings) {
    int k = 0;
    while (hi - lo > 1e-12) {
        double mid = (lo + hi) / 2.0;
        if (f(lo) * f(mid) <= 0.0) hi = mid;   /* signs differ: the crossing is in [lo, mid] */
        else                       lo = mid;
        k++;
    }
    *halvings = k;
    return (lo + hi) / 2.0;
}

Now the same code solves all three, and the only thing that changes is f.

This is what a function buys you. Not shorter code — a boundary, with the problem on one side and the method on the other.

Tuesday — a universe with one rule

10 · Start with the world, not the syntax

A grid of cells, each alive or dead. Nothing moves and nothing is drawn. Every cell looks at its eight neighbours and decides what to be next. That is the whole game — nobody plays it.

The array comes after the world. Decide what you are modelling; the declaration follows.

#define ROWS 8
#define COLS 8

int world[ROWS][COLS] = {0};      /* every cell dead, to begin */
written valid?
world[0][0] yes — the first cell
world[7][7] yes — the last
world[8][8] no — there is no row 8

For [8] the valid indices are 0 … 7. C will not stop you writing world[8][8], and what happens then is undefined — not “whatever happens to be in that memory”.

10b · Handing a whole world to a function

Monday left you with two ways to pass something: by value, which copies, and by reference, which needs an &. An array is neither, and Tuesday’s code depends on it.

#define ROWS 3
#define COLS 4

void wipe(int m[ROWS][COLS]) { m[0][0] = 99; }   /* no & anywhere */
before wipe(g)  g[0][0] = 1
after  wipe(g)  g[0][0] = 99

No & anywhere — and the caller’s grid changed. You do not need the &, because an array’s name already hands over the location rather than the contents. That is why nextGeneration(world) can fill in a world without you writing &world, and why a function can never accidentally copy a grid for you.

The flip side: a function given a grid can always change it. With an int you know it cannot. With an array you have to read the function to find out.

And the parameter must carry the column count. These are the four ways you might write it, and only two of them compile:

parameter
int m[3][4] fine
int m[][4] fine — the row count is not needed
int m[3][] rejected
int m[][] rejected 
/tmp/t.c:2:13: error: array has incomplete element type 'int[]'

The reason is arithmetic. To reach m[1][0] the machine computes 1*COLS + 0 — a grid is one block of ROWS*COLS integers laid out row after row, and the column count is what turns a pair of subscripts into a position in it. Drop COLS and there is no sum to do. Drop ROWS and nothing is lost, because no part of that calculation uses it.

11 · Walking the world

void printWorld(int world[ROWS][COLS])
{
    for (int i = 0; i < ROWS; i++) {

        for (int j = 0; j < COLS; j++) {

            if (world[i][j])
                printf("##");
            else
                printf("  ");
        }

        printf("\n");
    }
}

Outer loop picks the row; inner loop walks its columns. The newline belongs to the outer loop, because it ends a row.

12 · The rule, in full

the cell is live neighbours it becomes
alive 2 or 3 alive
alive anything else dead
dead exactly 3 alive
dead anything else dead

Local rules only. No cell can see further than one step away.

13 · Counting one cell’s neighbours

int countNeighbours(int world[ROWS][COLS], int i, int j)
{
    int count = 0;

    for (int di = -1; di <= 1; di++) {

        for (int dj = -1; dj <= 1; dj++) {

            if (di == 0 && dj == 0)
                continue;

            int ni = i + di;
            int nj = j + dj;

            if (ni >= 0 && ni < ROWS &&
                nj >= 0 && nj < COLS) {

                count += world[ni][nj];
            }
        }
    }

    return count;
}

di and dj run over relative coordinates: −1, 0, +1. Nine combinations, minus yourself, is eight neighbours. The continue skips yourself; the if above the sum is what keeps you from reading off the edge.

That second test is not optional. A corner cell has only three neighbours, and without the bounds check you read world[-1][-1] — outside the array, and undefined. It will very often appear to work, which is exactly the danger.

14 · The bug that matters most

for (int i = 0; i < ROWS; i++)
    for (int j = 0; j < COLS; j++) {
        int neighbours = countNeighbours(world, i, j);
        if (neighbours < 2) world[i][j] = 0;    /* writing into the world */
        /* ... */
    }

Cell (0,0) is decided and written back. Cell (0,1) then counts its neighbours — and one of them has already changed. Every cell in a generation must see the same old world.

next = f(current). You cannot let current change while f is still reading it.

So you need two grids:

void nextGeneration(int world[ROWS][COLS])
{
    int next[ROWS][COLS];

    for (int i = 0; i < ROWS; i++) {

        for (int j = 0; j < COLS; j++) {

            int neighbors =
                countNeighbours(world, i, j);

            if (world[i][j] == 1) {

                if (neighbors == 2 ||
                    neighbors == 3)

                    next[i][j] = 1;

                else
                    next[i][j] = 0;

            } else {

                if (neighbors == 3)
                    next[i][j] = 1;

                else
                    next[i][j] = 0;
            }
        }
    }


    /* Copy next generation back */

    for (int i = 0; i < ROWS; i++) {

        for (int j = 0; j < COLS; j++) {

            world[i][j] = next[i][j];
        }
    }
}

After Class

  • sin and cos by their series. cos x = 1 − x²/2! + x⁴/4! − …. Write it two ways: computing each factorial, and building each term from the one before with term *= -x*x/((2i+1)(2i+2)). Then find where the first way breaks. A hint you can check in one line: 12! is 479001600 and fits an int; 13! is 6227020800 and does not. 20! still fits a long long; 21! does not. The incremental form never builds a factorial at all.
  • Then try ln. The obvious series is ln(1+u) = u − u²/2 + u³/3 − …. Try it at x = 8 and watch what happens.

Going Further · What sin(x) Actually Does

The After-Class exercise above asks you to build cos from its series. This section follows that one step further, with sin, and shows why the series is the starting point and not the answer. Every output below is real.

The series

sin x = x − x³/3! + x⁵/5! − x⁷/7! + x⁹/9! − …

which is the same pattern as cos, starting at x instead of 1. As with cos, never build the factorials — grow each term from the one before it:

#include <stdio.h>
#include <math.h>

/* The series, with each term built from the one before.
   No factorial is ever formed, so nothing overflows. */
double mySin(double x, int terms)
{
    double term = x, sum = 0.0;

    for (int k = 0; k < terms; k++) {
        sum += term;
        term = term * (-x * x) / ((2*k + 2) * (2*k + 3));
    }
    return sum;
}

int main(void)
{
    double xs[5] = { 0.1, 1.0, 10.0, 100.0, 1000000.0 };

    for (int i = 0; i < 5; i++)
        printf("x = %-9g mine = %-14.6g  sin(x) = %-12.6g  error = %.3g\n",
               xs[i], mySin(xs[i], 12), sin(xs[i]),
               fabs(mySin(xs[i], 12) - sin(xs[i])));
    return 0;
}

Compile it with -lm. Predict the five lines before you look.

x = 0.1       mine = 0.0998334       sin(x) = 0.0998334     error = 1.39e-17
x = 1         mine = 0.841471        sin(x) = 0.841471      error = 0
x = 10        mine = -1.10708        sin(x) = -0.544021     error = 0.563
x = 100       mine = -3.68039e+23    sin(x) = -0.506366     error = 3.68e+23
x = 1e+06     mine = -3.86817e+115   sin(x) = -0.349994     error = 3.87e+115

Perfect at 0.1 and 1. Wrong in the first decimal at 10. At 100 the answer is off by 23 orders of magnitude, and sin is a function that never leaves −1 … 1.

“Use more terms” is not the fix

The obvious reaction is that twelve terms is too few. That reaction is right at x = 10 and wrong everywhere past it. Run the same series with more terms:

terms x = 10 x = 100 x = 1000000
12 −1.1071 −3.68e+23 −3.87e+115
30 −0.5440211109 −5.35e+37 −7.21e+273
60 −0.5440211109 −7.37e+40 nan
200 −0.5440211109 −8.26e+25 nan
600 −0.5440211109 −8.26e+25 nan
true −0.5440211109 true −0.5063656411 true −0.3499935022

At x = 10, thirty terms lands it. At x = 100, no number of terms ever will — the value settles on 8.26e+25 and stays there.

The reason is not the mathematics. The series converges for every x; a mathematician is not wrong. The reason is the arithmetic. At x = 100 the largest single term the sum ever forms is about 1.07e+42, and those giant terms have to cancel each other down to an answer of about 0.5. A double carries roughly 16 significant digits. Cancelling 42 digits down to one, with 16 digits to work in, leaves nothing but the rounding error.

A convergent series and a usable algorithm are two different things.

So what does math.h give you?

When you write #include <math.h> and call sin(x), the header supplies little more than the promise — the same kind of promise §2 was about:

double sin(double x);

The body lives in the platform’s maths library, libm, which the linker pulls in when you pass -lm. The C standard says what sin must do; it does not say how. Different machines may compute it differently, and a good implementation is doing something like this:

x  →  range reduction  →  small argument  →  polynomial  →  result

Step 1 · Range reduction

The series is only in trouble because x got large. So make it small first, using the one thing sin is famous for:

sin(x + 2πk) = sin x

Better still, reduce modulo π/2 rather than 2π. Write x = n·(π/2) + r, choosing the nearest n so that |r| is at most about π/4. Then n mod 4 says which function to call:

n mod 4 the answer is
0 sin r
1 cos r
2 −sin r
3 −cos r

The library now needs to be accurate on one small interval only, and never anywhere else.

Step 2 · A polynomial on the small interval

On −π/4 … π/4 a handful of terms is plenty. Four of them, written out:

double sinSmall(double x) {
    double z = x * x;
    return x - x*z/6.0 + x*z*z/120.0 - x*z*z*z/5040.0;
}

Measured against sin at 200001 points across −π/4 … π/4, its worst error is 3.12e-07. Adding one more term and rearranging into Horner’s form — factor out r, then keep peeling off a z:

double sinSmallHorner(double r) {
    double z = r * r, p;
    p =  1.0/362880.0;
    p = -1.0/5040.0  + z*p;
    p =  1.0/120.0   + z*p;
    p = -1.0/6.0     + z*p;
    return r + r*z*p;
}

Worst error over the same interval: 1.75e-09. Note what Horner’s form bought — z = r*r is computed once, and there is no r*r*r*r*r*r*r anywhere. Same polynomial, fewer multiplications, less rounding.

Putting the two together

#include <stdio.h>
#include <math.h>

double sinSmall(double x) {
    double z = x * x;
    return x - x*z/6.0 + x*z*z/120.0 - x*z*z*z/5040.0;
}
double cosSmall(double x) {
    double z = x * x;
    return 1.0 - z/2.0 + z*z/24.0 - z*z*z/720.0 + z*z*z*z/40320.0;
}

double mySin(double x)
{
    double n = floor(x / (M_PI/2) + 0.5);   /* nearest multiple of pi/2 */
    double r = x - n * (M_PI/2);            /* what is left over        */
    int q = (int) fmod(n, 4.0);
    q = ((q % 4) + 4) % 4;                  /* fmod can come back negative */

    if (q == 0) return  sinSmall(r);
    if (q == 1) return  cosSmall(r);
    if (q == 2) return -sinSmall(r);
    return              -cosSmall(r);
}

int main(void)
{
    double xs[7] = { 0.1, 1.0, 3.0, 10.0, 100.0, 1000000.0, 1e20 };

    for (int i = 0; i < 7; i++)
        printf("x = %-9g mine = %-14.6g  sin(x) = %-12.6g  error = %.3g\n",
               xs[i], mySin(xs[i]), sin(xs[i]), fabs(mySin(xs[i]) - sin(xs[i])));
    return 0;
}
x = 0.1       mine = 0.0998334       sin(x) = 0.0998334     error = 2.75e-15
x = 1         mine = 0.841471        sin(x) = 0.841471      error = 1.01e-09
x = 3         mine = 0.14112         sin(x) = 0.14112       error = 6.31e-14
x = 10        mine = -0.544021       sin(x) = -0.544021     error = 1.89e-08
x = 100       mine = -0.506366       sin(x) = -0.506366     error = 9.22e-09
x = 1e+06     mine = -0.349994       sin(x) = -0.349994     error = 2.99e-10
x = 1e+20     mine = -6.10268e+20    sin(x) = -0.645251     error = 6.1e+20

Compare the x = 1e+06 line with the one at the top of this section: error 3.87e+115 has become 2.99e-10, and the only new idea was to make the argument small before doing anything with it.

Where this one still breaks

The last line. At x = 1e20 the reduction itself falls apart, and it is the same disease in a new place. Reducing means computing x - n*(M_PI/2), and at that size n is about 6.4e+19. Every rounding error in n * (M_PI/2) is multiplied by how big n is:

x n error in n * (M_PI/2)
100 64 2.23e-14
1e+06 636620 2.22e-10
1e+12 636619772368 0.000222
1e+20 63661977236758134784 2.22e+04

r is supposed to come out no bigger than π/4 ≈ 0.785. At x = 1e20 this code produces r = 3150. There is no accuracy left to lose, because the subtraction has taken two huge nearly-equal numbers and kept only their noise. Real libraries carry π to hundreds of bits for exactly this case.

One last honesty

Everything above used the Taylor coefficients, because you can derive them. A production library usually does not. Taylor coefficients are chosen to be as accurate as possible at one point, x = 0. A library wants the worst error across the whole interval −π/4 … π/4 to be as small as possible, which is a different request and gives slightly different numbers. That family of approximations is called minimax, and it is a topic for another year — but it is why the constants inside a real sin are not the ones you recognise.

So sin(x) — three characters, one return value — is standing on calculus, polynomial approximation, how a double is stored, range reduction, and a choice of algorithm. That is what a function being a promise really buys you: all of that, kept behind a name.

Going Further · And What sqrt(x) Does

§6 found √5 by halving an interval. That works, and §9 showed it works for any f once you ask the right question. But it is not how anyone computes a square root when they are in a hurry, and sqrt is worth its own look because it ends somewhere sin does not.

As with sin, math.h only declares the promise:

double sqrt(double x);

The standard says what sqrt must produce, not how. Every output below is real.

Turn the square root into a root

We want x = √a, which is the same as saying x² = a, which is the same as saying

f(x) = x² − a  is zero.

That is §9’s question again, so §9’s answer is available — halve the bracket. Newton’s method asks a different one: stand at your guess, follow the tangent line down to zero, and go there. That gives

x ← x − f(x)/f′(x)

and with f(x) = x² − a, so f′(x) = 2x, the whole thing collapses to

x ← ½ · (x + a/x)

Read it as an average. If your guess x is too small, then a/x is too big, and the true root is somewhere between them — so take the midpoint and go round again. The Babylonians knew this; it is about four thousand years old.

Watch it run

#include <stdio.h>
#include <math.h>

int main(void)
{
    double x = 1.0, truth = sqrt(2.0);

    for (int i = 0; i < 6; i++) {
        printf("x%d = %.16f   error = %.3g\n", i, x, fabs(x - truth));
        x = 0.5 * (x + 2.0 / x);
    }
    printf("     %.16f   <- sqrt(2.0)\n", truth);
    return 0;
}

Look at the error column, not the digits: 0.4, then 0.09, then 0.002, then 2e-06, then 1.6e-12. Each step roughly doubles the number of correct digits — 0.4, 1.1, 2.6, 5.7, 11.8, 15.7 of them. Five steps from a guess of 1 exhausts what a double can hold.

Against §6’s halving

Both methods find the same number. They do not find it at the same speed.

a halving, to a bracket of 1e-12 Newton, from x = a
2 41 steps 6 steps
5 43 steps 7 steps
100 47 steps 9 steps

Halving buys exactly one bit per step — it is the same one bit whether you are close or far. Newton squares the error each step, so once it is near, it arrives almost at once. That is the whole difference, and it is why §6 is the method you can always trust and this is the method you actually use.

The ten-line version, and where it lets you down

The obvious way to package it:

double my_sqrt(double a)
{
    double x = a;
    for (int i = 0; i < 10; i++)
        x = 0.5 * (x + a / x);
    return x;
}

Ten iterations, no thinking required. Try it across a range of inputs before you trust it:

#include <stdio.h>
#include <math.h>

/* the obvious version: start at a, iterate a fixed ten times */
double my_sqrt(double a)
{
    double x = a;
    for (int i = 0; i < 10; i++)
        x = 0.5 * (x + a / x);
    return x;
}

/* split off the exponent first, then five steps on the significand */
double my_sqrt2(double a)
{
    if (a <  0.0) return NAN;
    if (a == 0.0) return 0.0;

    int e;
    double m = frexp(a, &e);         /* a = m * 2^e, with 0.5 <= m < 1 */
    if (e % 2) { m *= 2.0; e -= 1; } /* force e even, so 0.5 <= m < 2  */

    double x = 1.0;                  /* now always a good first guess  */
    for (int i = 0; i < 5; i++)
        x = 0.5 * (x + m / x);

    return ldexp(x, e / 2);          /* put the exponent back          */
}

int main(void)
{
    double as[6] = { 1e-8, 2.0, 100.0, 1e6, 1e12, 1e100 };

    printf("%-8s %-16s %-16s %-16s\n", "a", "my_sqrt", "my_sqrt2", "sqrt");
    for (int i = 0; i < 6; i++)
        printf("%-8.0e %-16.8g %-16.8g %-16.8g\n",
               as[i], my_sqrt(as[i]), my_sqrt2(as[i]), sqrt(as[i]));
    return 0;
}

1e+100   9.765625e+96     1e+50            1e+50

my_sqrt(1000000.0) returns 1296.19. Not nearly a thousand — a different number altogether, from code that is correct at a = 2 and a = 100.

Nothing is wrong with the iteration. Ten of them is simply not enough, because the starting guess x = a is a million when the answer is a thousand. Newton spends its early steps just halving the guess down to the right size, and only then starts doubling digits. Count the steps to converge:

a 2 100 1e6 1e12 1e100
steps from x = a 6 9 16 26 172

The number of iterations grows with the size of a. Any fixed count is wrong for a large enough input.

Which is exactly why the exponent matters

A double is already stored as a significand times a power of two,

a = m · 2^e

and the square root of that is

√a = √m · 2^(e/2)

so if you make e even, half the problem is solved by dividing an integer by two. What is left, √m, is a square root of a number between 0.5 and 2 — where a guess of 1.0 is never far off. frexp hands you m and e; ldexp puts them back together.

That is my_sqrt2 above, and the column speaks for itself: correct from 1e-8 to 1e100, on five iterations rather than 172. The exponent trick is not an elegance. It is what makes a fixed, small iteration count possible at all.

If 8 = 2 × 2² makes this concrete: √8 = √2 × 2 = 2.828427124746190, and sqrt(8.0) returns 2.828427124746190. The hard part was only ever √2.

This is the shape sin had, arrived at from a different direction:

Reduce to a small, controlled range · approximate well there · reassemble.

How close is close?

Tested against sqrt on 200000 values spread from 1e-200 to 1e200, my_sqrt2 disagrees on 25.1% of them — and the worst disagreement is 1.00 ULP, one unit in the last place.

So it is right to the last bit, and still not correctly rounded. A real library must return the nearest representable double every single time, which is a stronger promise than “very close”, and getting that last bit right is the final step in a production implementation. That is the difference between a good classroom answer and a library.

Where sqrt parts company with sin

There is no machine instruction for sine. There is one for square root. Compile

#include <math.h>
double f(double x){ return sqrt(x); }

with gcc -O2 -S and read the assembly. On the machine these notes were written on, the entire function body is one instruction:

fsqrt   d0, d0

On the x86 lab machines you should find sqrtsd instead — run it yourself and look. Either way, all the Newton machinery above has been replaced by a single operation in silicon, which is why sqrt is fast and why the library rarely computes it the way you just did.

That does not make the exercise pointless — it makes it the point. Square root feels like a primitive, something the machine simply knows. It is not. It is +, × and /, arranged so that each step doubles what you already have, and someone eventually put that arrangement into hardware.

One warning before you use it anywhere

my_sqrt is ten lines and it is not a sqrt. Besides the size problem above:

a my_sqrt(a) sqrt(a)
0.0 nan — the first step divides by zero 0
−4.0 −4.80176, a number that looks like an answer nan

The negative case is the dangerous one: it does not crash and it does not warn. It returns a plausible-looking value that is not a square root of anything. A library function has to handle zero, negatives, infinities, NaNs and subnormals before it may be called sqrt.

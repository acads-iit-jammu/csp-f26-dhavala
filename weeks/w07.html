In Class

Monday — why an array at all, and eight questions about one bank account.

ImportantThe sentence the whole week turns on

A variable remembers the current value. An array remembers a history.

Everything below follows from asking a question that a single number cannot answer.

Code You Can Copy

Every program here was compiled and run before it was printed; the outputs are what it actually produced. Predict each one before you run it.

1 · When a single variable is enough — and when it stops being enough

A bank account needs one number:

int balance = 10000;
balance = balance + 2000;      /* a deposit */
balance = balance - 5000;      /* a withdrawal */

That answers “what is the balance now?” perfectly, and it will answer it forever.

Now ask a different question:

  • What was the balance five transactions ago?
  • On which day was it lowest?
  • Did the account ever go negative?
  • Which single transaction took the most money out?

Not one of these can be answered by the variable above. Each assignment destroyed the previous value, so the information is simply gone.

But be precise about what would fix it, because “use an array” is not the only answer. If you knew the question in advance, you could carry a little extra as you went: a lowest and the day it happened, a wentNegative flag, a previous balance to compare against. Three of the four questions above fall to that, in one pass, with no array at all.

The array earns its place the moment you do not know what you will be asked. Keep the history and every one of those questions — and the ones nobody has thought of yet — is still answerable. Throw it away and you are betting that you already know what will matter.

2 · The data: two arrays that move together

#include <stdio.h>

int main(void) {
    int date[]    = { 1,     3,     5,    8,    12,    15,   18,   22,   25,   29 };
    int balance[] = { 10000, 12000, 9500, 7000, 3000, -3000, 2000, 1500, 9000, 2500 };
    int n = 10;

    for (int i = 0; i < n; i++)
        printf("Day %2d : balance = %6d\n", date[i], balance[i]);

    return 0;
}
Day  1 : balance =  10000     Day 15 : balance =  -3000
Day  3 : balance =  12000     Day 18 : balance =   2000
Day  5 : balance =   9500     Day 22 : balance =   1500
Day  8 : balance =   7000     Day 25 : balance =   9000
Day 12 : balance =   3000     Day 29 : balance =   2500

These are parallel arrays: date[i] and balance[i] describe the same transaction. The index is what binds them. Nothing in C enforces that — it is a promise you are making, and it is your job to keep it.

For an array of n elements the valid indices are 0 … n-1. There is no balance[n], and C will not stop you from asking for it. What happens then is undefined — not “you get whatever was in that memory”. The program may print rubbish, may crash, may behave differently once you compile with optimisation, and may appear to work for a year and then not. There is no rule you can rely on, which is exactly why the boundary is yours to keep.

3 · Did the account ever go negative?

    for (int i = 0; i < n; i++) {
        if (balance[i] < 0) {
            printf("went negative on day %d\n", date[i]);
            break;                       /* one example is enough */
        }
    }
went negative on day 15

A loop that sets a flag and keeps scanning would answer just as correctly — so the break is not what makes this right. What it says is that the work is finished: “did it ever?” needs one witness, and searching on after you have found it buys nothing. Knowing when you may stop is a claim about the question, not about the code.

4 · The same data, three questions, three loops

This is the idea to take away from today:

/* (a) find ALL of them  — no break */
for (int i = 0; i < n; i++)
    if (balance[i] < 0) printf("negative on day %d\n", date[i]);

/* (b) find the FIRST — break on the first hit */
for (int i = 0; i < n; i++)
    if (balance[i] < 0) { printf("first on day %d\n", date[i]); break; }

/* (c) did it EVER? — a yes/no, so remember a flag */
int ever = 0;
for (int i = 0; i < n; i++)
    if (balance[i] < 0) { ever = 1; break; }
printf(ever ? "yes\n" : "no\n");

Same array, same test, three different loops — because they are three different questions. The control structure follows from the question, never the other way round.

5 · A corrupted record, and why continue earns its keep

Suppose the bank’s file marks an unreadable record with -999999, and day 22 is corrupt:

    int balance[] = { 10000, 12000, 9500, 7000, 3000, -3000, 2000, -999999, 9000, 2500 };

Now find the lowest balance. Naively:

    int low = balance[0], at = 0;
    for (int i = 1; i < n; i++)
        if (balance[i] < low) { low = balance[i]; at = i; }
    printf("lowest = %d on day %d\n", low, date[at]);
lowest = -999999 on day 22

That is not a bank balance; it is a flag pretending to be data, and it has quietly become the answer. The fix is one line — refuse to process a record you do not trust:

    int low = 0, at = -1;
    for (int i = 0; i < n; i++) {
        if (balance[i] == -999999) continue;      /* not data. skip it. */
        if (at == -1 || balance[i] < low) { low = balance[i]; at = i; }
    }
    printf("lowest = %d on day %d\n", low, date[at]);
lowest = -3000 on day 15

continue says “this record is of no interest — the rest still are.” break says “there is no point looking at the rest.” Choosing the wrong one here does not crash anything; it gives you a confident, wrong answer.

6 · The best-so-far pattern, and why you keep the index

    int low = balance[0], at = 0;
    for (int i = 1; i < n; i++)
        if (balance[i] < low) { low = balance[i]; at = i; }

    printf("lowest = %d, on day %d\n", low, date[at]);
lowest = -3000, on day 15

Two details worth arguing about. The loop starts at i = 1, because element 0 is already the best-so-far — starting at 0 works too, but compares it with itself. And we remember at, not just low: the index is what lets us get back to date[]. An answer of “−3000” is not useful; “−3000, on day 15” is.

7 · Neighbours: what each transaction actually did

A balance history does not record the transactions — but it implies them:

    for (int i = 1; i < n; i++) {
        int change = balance[i] - balance[i-1];

        if      (change > 0) printf("Day %2d: deposit    %6d\n", date[i],  change);
        else if (change < 0) printf("Day %2d: withdrawal %6d\n", date[i], -change);
        else                 printf("Day %2d: no change\n",      date[i]);
    }
Day  3: deposit      2000      Day 18: deposit      5000
Day  5: withdrawal   2500      Day 22: withdrawal    500
Day  8: withdrawal   2500      Day 25: deposit      7500
Day 12: withdrawal   4000      Day 29: withdrawal   6500
Day 15: withdrawal   6000

Why does this loop start at i = 1? Because it reads balance[i-1], and at i = 0 that is balance[-1] — outside the array, and undefined. Whenever a loop looks at a neighbour, one end of the range has to give.

8 · Three questions that sound the same and are not

    /* the biggest single drop */
    int drop = 0, di = -1;
    for (int i = 1; i < n; i++) {
        int change = balance[i] - balance[i-1];
        if (change < drop) { drop = change; di = i; }
    }
    if (di != -1) printf("largest drop: %d on day %d\n", -drop, date[di]);

    /* every drop over 5000 — worth a look */
    for (int i = 1; i < n; i++)
        if (balance[i] - balance[i-1] < -5000)
            printf("large debit on day %d\n", date[i]);

    /* over 5000 AND it left the account overdrawn */
    for (int i = 1; i < n; i++)
        if (balance[i] - balance[i-1] < -5000 && balance[i] < 0)
            printf("large debit that overdrew the account: day %d\n", date[i]);
largest drop: 6500 on day 29
large debit on day 15
large debit on day 29
large debit that overdrew the account: day 15

Look at what the three answers actually are. The largest drop is on day 29 — and it is not the one that matters. Day 15 is the transaction that overdrew the account. “Biggest” and “worst” are different questions, and the && is what separates them.

ImportantNow run the same three loops on the corrupted array from §5

One record — day 22, holding -999999 — and the output becomes:

largest drop: 1001999 on day 22
large debit on day 15
large debit on day 22
large debit on day 29
large debit that overdrew the account: day 15
large debit that overdrew the account: day 22

Every one of the three answers is now wrong, and two of them are wrong in a way that looks entirely plausible if you do not know the data. In §5 we fixed the minimum by putting a continue in that loop — but here are three more loops, each of which would need its own.

And §7’s loop is worse than it looks. Skipping the pass where balance[i] is corrupt is not enough — the next pass still reads that same value as balance[i-1]. One bad record poisons two differences, not one.

So what is the change across a missing day? Skip both differences? Bridge from the last good balance to the next good one? Declare the series unusable? Those are not coding decisions. They are decisions about what the data means, and no one can make them from inside the loop.

Which is the real lesson. A record you cannot trust is worth settling once, before any analysis runs, rather than re-excluding it in every loop that touches the array — but settling it means first deciding what it means, and that is a conversation, not a continue.

Tuesday — two arrays that mean different things, and one grid.

Monday’s history had one account. Today: a test rig with four thermocouples, logged hourly — which is the shape of almost every measurement you will ever be handed.

#define S 4                                   /* four probes        */
#define H 8                                   /* eight hourly reads */

int sensorID[S] = { 101, 102, 103, 104 };     /* parallel 1-D arrays  */
int ratedMax[S] = { 250, 300, 220, 340 };     /* each probe's own limit */

int temp[S][H] = {                            /* a 2-D array          */
    { 240, 242, 245, 248, 258, 247, 244, 241 },
    { 180, 265, 190, 195, 215, 200, 195, 190 },
    { 210, 215, 220, 225, 245, 228, 222, 218 },
    { 200, 205, 210, 215, 235, 218, 212, 208 },
};

9 · Why a second index, and not a fifth array

You could keep four separate arrays — probe0[], probe1[], probe2[], probe3[]. It works. Until someone asks:

At which hour was the rig, as a whole, hottest?

Take “as a whole” to mean the total across the four probes — that reading is a choice, and we come back to it below, because it is not the only one. Under it, this is a question about a column: you must add probe0[h] + probe1[h] + probe2[h] + probe3[h]. With four probes that is one line. With forty it is forty terms, written out by hand — because you cannot loop over variable names. You can loop over an index:

    int hottest = 0, best = -1;

    for (int h = 0; h < H; h++) {
        int total = 0;
        for (int s = 0; s < S; s++)          /* down the column */
            total += temp[s][h];

        if (total > best) { best = total; hottest = h; }
    }
    printf("hour %d, total %d across all %d sensors\n", hottest, best, S);
hour 4, total 953 across all 4 sensors

That is the entire case for two dimensions, and it is the same move you made on Monday, one storey up:

from to what changed
many variables one array the index replaced the name
many arrays one table a second index replaced the array name

temp[s][h] reads “probe s, hour h”. The first index picks the row, the second the position along it.

10 · Which array holds what — and why they are not all 2-D

Two different questions decide this, and it helps to keep them apart.

First: how many indices does one value need?

one value is… so
sensorID[s] one ID per sensor one index
ratedMax[s] one limit per sensor one index
temp[s][h] one reading per sensor, per hour two indices

That — and only that — is what makes temp two-dimensional. Count the axes.

Second: should things sharing an index live in the same array? All three above are indexed by s, so you could try to merge them. Don’t: an array holds one type, and data[0][s] holding an ID while data[1][s] holds degrees is a lie the compiler cannot catch — nothing will warn you when you average them together. Different quantities about the same thing stay in separate arrays that move together.

(That is clumsy, and the clumsiness has a proper fix called a struct. Later.)

11 · One line that needs both

    for (int s = 0; s < S; s++)
        for (int h = 0; h < H; h++)
            if (temp[s][h] > ratedMax[s])
                printf("sensor %d (rated %d) hit %d at hour %d\n",
                       sensorID[s], ratedMax[s], temp[s][h], h);
sensor 101 (rated 250) hit 258 at hour 4
sensor 103 (rated 220) hit 225 at hour 3
sensor 103 (rated 220) hit 245 at hour 4
sensor 103 (rated 220) hit 228 at hour 5
sensor 103 (rated 220) hit 222 at hour 6

temp[s][h] is the grid, ratedMax[s] is the parallel array, and s is the same index in both. That is what the two structures are for, and how they cooperate.

Note what a simpler question would have missed. “What was the highest reading?” answers 265, on sensor 102 — which was nowhere near its limit of 300. The probe in trouble was 103, at 245. The threshold lives in the other array. Highest is not the same as worst.

12 · The same rig as a control chart — and what the picture is for

Industry does not read sensor logs as columns of numbers. It plots them, and it draws two lines on the plot: an upper control limit and a lower control limit. A reading between them is normal variation and means nothing. A reading outside them is a signal — something changed.

Here is a process line with four different kinds of sensor, sampled once a minute for sixteen minutes. Each has its own units and its own limits, so the limits live in parallel 1-D arrays while the readings need a grid:

#include <stdio.h>

#define S 4
#define T 16
#define ROWS 9

const char *name[S] = { "furnace temp", "line pressure", "vibration", "coolant flow" };
const char *unit[S] = { "C",            "kPa",           "um",        "L/min"        };
int lcl[S] = { 180, 400,  5,  90 };
int ucl[S] = { 260, 700, 45, 130 };
int r[S][T] = {
  { 205,208,212,210,215,222,231,244,252,263,258,247,236,228,220,214 },
  { 512,508,515,521,509,498,505,517,523,530,527,519,511,505,499,504 },
  {  12, 14, 11, 13, 15, 14, 18, 26, 34, 47, 52, 44, 31, 22, 16, 13 },
  { 118,117,119,116,118,115,112,107,101, 95, 88, 92, 99,105,111,115 },
};

Drawing it is nothing but the nested loops of this week — one loop down the rows of the plot, one across time — asking of each cell does a point belong here?

int main(void) {
    for (int s = 0; s < S; s++) {
        int pad = (ucl[s] - lcl[s]) / 8;
        int lo = lcl[s] - pad, hi = ucl[s] + pad;

        printf("%s (%s)   LCL %d   UCL %d\n", name[s], unit[s], lcl[s], ucl[s]);
        for (int row = ROWS - 1; row >= 0; row--) {
            int level = lo + row * (hi - lo) / (ROWS - 1);
            int isU = (ucl[s] - lo) * (ROWS - 1) / (hi - lo) == row;
            int isL = (lcl[s] - lo) * (ROWS - 1) / (hi - lo) == row;
            printf("%6d %c", level, (isU || isL) ? '+' : '|');
            for (int t = 0; t < T; t++) {
                int rr = (r[s][t] - lo) * (ROWS - 1) / (hi - lo);
                int bad = r[s][t] > ucl[s] || r[s][t] < lcl[s];
                if (rr == row)          putchar(bad ? '!' : '*');
                else if (isU || isL)    putchar('-');
                else                    putchar(' ');
            }
            printf("%s\n", isU ? " UCL" : isL ? " LCL" : "");
        }
        printf("       +");
        for (int t = 0; t < T; t++) putchar('-');
        printf("\n        minute 1 ......... 16\n\n");
    }

    /* the whole point of the limits: which readings were out of control? */
    printf("out of control:\n");
    for (int s = 0; s < S; s++)
        for (int t = 0; t < T; t++)
            if (r[s][t] > ucl[s] || r[s][t] < lcl[s])
                printf("  minute %2d  %-14s %4d %-5s  (limits %d..%d)\n",
                       t + 1, name[s], r[s][t], unit[s], lcl[s], ucl[s]);
    return 0;
}

Now look at the three charts together. Coolant flow falls, furnace temperature climbs, vibration spikes, all inside two minutes. Not one of those charts shows that on its own. It appears only when you hold the time fixed and look across the sensors — which is a loop with its axes the other way round from every loop so far this week:

    /* Walk TIME on the outside and SENSORS on the inside - the opposite
       order to every loop so far this week. That swap is the question. */
    for (int t = 0; t < T; t++) {
        int out = 0;
        for (int s = 0; s < S; s++)
            if (r[s][t] > ucl[s] || r[s][t] < lcl[s]) out++;
        if (out >= 2) {
            printf("minute %2d: %d sensors out --", t + 1, out);
            for (int s = 0; s < S; s++)
                if (r[s][t] > ucl[s] || r[s][t] < lcl[s]) printf(" %s", name[s]);
            printf("\n");
        }
    }

minute 11: 2 sensors out -- vibration coolant flow

That is the question the grid exists to answer. Four separate arrays could have drawn all four charts perfectly well; only the grid lets you ask what happened at one moment across all of them.

13 · When is a column allowed to mean anything?

Section 10 asked how many indices a value needs. That settles the shape. It does not settle which operations are legal, and the difference matters.

Ask the plant manager’s question: “which sensor is the worst?” The obvious program hunts for the biggest excursion beyond a limit. But the furnace is over by 3, in degrees, and vibration is over by 7, in micrometres — and 7 is not bigger than 3 in any physical sense. The only comparable quantity is each excursion measured against that sensor’s own band:

    printf("sensor           worst reading   over by   as %% of its own band\n");
    for (int s = 0; s < S; s++) {
        int over = 0, val = 0;                  /* biggest excursion, any direction */
        for (int t = 0; t < T; t++) {
            int e = 0;
            if (r[s][t] > ucl[s]) e = r[s][t] - ucl[s];
            if (r[s][t] < lcl[s]) e = lcl[s] - r[s][t];
            if (e > over) { over = e; val = r[s][t]; }
        }
        int band = ucl[s] - lcl[s];
        printf("%-14s %6d %-5s %7d %14d%%\n",
               name[s], over ? val : 0, unit[s], over, 100 * over / band);
    }
sensor           worst reading   over by   as % of its own band
furnace temp      263 C           3              3%
line pressure       0 kPa         0              0%
vibration          52 um          7             17%
coolant flow       88 L/min       2              5%

The two orderings genuinely disagree. By raw excursion the furnace (3) looks worse than the coolant (2); by share of its own band the coolant (5%) is worse than the furnace (3%). Neither ordering is wrong — but only one of them is a comparison at all.

Now change one thing. Put four sensors of the same kind on one machine — four vibration probes, one per bearing. Same units, same scale, so one pair of limits serves all four and the parallel array disappears:

#include <stdio.h>

#define B 4                 /* four bearings on ONE machine        */
#define T 16                /* same sixteen minutes                */

/* Same kind of sensor on every bearing: same units, SAME limits.
   So one pair of numbers serves all four - no parallel array needed. */
#define LCL 5
#define UCL 45
int main(void) {
    int v[B][T] = {
      { 12, 14, 11, 13, 15, 14, 18, 26, 34, 47, 52, 44, 31, 22, 16, 13 },
      { 10, 11, 13, 12, 11, 13, 14, 17, 21, 28, 33, 27, 19, 15, 12, 11 },
      {  9, 10,  9, 11, 10, 12, 11, 13, 15, 18, 20, 17, 14, 12, 10,  9 },
      { 11, 12, 12, 10, 13, 11, 12, 14, 16, 19, 22, 18, 15, 13, 11, 10 },
    };

    /* Because the units agree, BOTH directions are meaningful. */
    printf("minute  B1  B2  B3  B4   mean across bearings\n");
    for (int t = 0; t < T; t++) {
        int sum = 0;
        printf("%5d ", t + 1);
        for (int b = 0; b < B; b++) { printf("%4d", v[b][t]); sum += v[b][t]; }
        printf("%12d%s\n", sum / B, sum / B > 25 ? "   <- machine-wide" : "");
    }

    printf("\nper bearing, across the whole run:\n");
    for (int b = 0; b < B; b++) {
        int mx = v[b][0], at = 0, bad = 0;
        for (int t = 0; t < T; t++) {
            if (v[b][t] > mx) { mx = v[b][t]; at = t; }
            if (v[b][t] > UCL || v[b][t] < LCL) bad++;
        }
        printf("  B%d  peak %2d at minute %2d   %d reading(s) out of control\n",
               b + 1, mx, at + 1, bad);
    }
    return 0;
}

   14   22  15  12  13          15
   15   16  12  10  11          12
   16   13  11   9  10          10

per bearing, across the whole run:
  B1  peak 52 at minute 11   2 reading(s) out of control
  B2  peak 33 at minute 11   0 reading(s) out of control
  B3  peak 20 at minute 11   0 reading(s) out of control
  B4  peak 22 at minute 11   0 reading(s) out of control

sum / B is a real number here — the machine’s mean vibration — and on the mixed line the same expression would have been nonsense. That is the whole distinction:

four different sensors four of the same sensor
limits one pair per sensor — a parallel array one pair for all — two constants
along a row (time) meaningful meaningful
down a column meaningless — you cannot average °C with µm the machine’s mean, a real number
the grid is storage that happens to be rectangular genuinely two-dimensional

Two arrays can have the same shape and not permit the same operations. What decides it is whether the rows are measured in the same thing.

A twelve-lead ECG is the same rectangle from medicine: twelve channels, one row each, all in microvolts on one time base — so comparing across leads is meaningful in a way comparing temperature to flow never is.

And the bearings hide the trap worth the whole session. B1 is the only bearing out of control — yet all four peak at minute 11. Replace B1 and you have treated a symptom: the synchronised peak says the cause was machine-wide, and the coolant chart says what it was. The worst reading and the thing that is wrong are not the same question.

14 · Questions a plant manager actually asks

Each of these is a real question, and each is imprecise in a way you must settle before you write a line of code. The ambiguity is not sloppiness on the manager’s part — it is the part of the job that is yours.

The question as asked What has to be decided first
“Is the process in control?” one bad reading, or a sustained excursion? Here that is 4 readings against 1 episode
“Which sensor is the worst?” most violations, biggest excursion, or biggest share of its band? §13 — and they disagree
“When did the trouble start?” the first reading outside a limit, or the first sign of drift? The furnace is climbing steadily from minute 5; it does not cross until minute 10
“Did they fail together?” §12 — and note minute 10 and minute 11 are different pairs of sensors
“How long were we out of control?” every minute with a violation, or the longest unbroken stretch?
“What is the average reading?” fine for the bearings; a unit error on the mixed line
“Is it getting worse?” compare the two halves, or count consecutive increases?
“Which bearing do we service?” the worst reading, or the actual cause? They are different bearings — and possibly no bearing at all

Take the third one seriously. A limit tells you when something has already gone wrong. The furnace was rising for five minutes before it crossed, and every one of those readings was, by the rule you were given, perfectly normal. Detecting the drift is a different program from detecting the breach, and the chart makes it obvious to the eye long before the ! appears.

Eight Words That Cost You a Day

Everything above was a precise question. Real ones are not. Here are four that a manager, a supervisor or a client might actually say — each one perfectly clear until you try to write it down.

“Which sensor is the hottest?”

Three honest programs, three different answers, from this same data:

you read it as answer
the highest average sensor 101 (245.6 °C)
the highest single reading sensor 102 (265 °C)
the most time spent above 230 sensor 101 (8 hours of 8)

None of these is a bug. Every one is a correct program. They disagree because the question does not say, and the person who asked it has a particular one in mind that they did not think to mention.

“At which hour was the rig hottest?”

you read it as answer
the highest total across the four probes hour 4
the hour holding the highest single reading hour 1

“How long was the rig above 230 °C?”

This is the one to sit with:

you read it as answer
hours where all probes were above 230 0
hours where any probe was above 230 8
hours where the average was above 230 2

Zero, eight, or two. Same data, same eleven words, three correct programs. If you hand in one of these and the answer wanted was another, nothing in your code is wrong — and no amount of testing your code against your own understanding will find it.

“How many exceeded the rating?”

you read it as answer
how many sensors ever exceeded theirs 2
how many readings were over the limit 5

What a Number Means Is Not in the Number

Suppose probe 104’s hour-2 reading comes back as -1.

Is that minus one degree, or is the probe disconnected?

If -1 is a real measurement, it belongs in the sum like any other:

    int sum = 0;
    for (int h = 0; h < H; h++)
        sum += temp[s][h];
    printf("average = %.1f\n", sum / (double) H);

If -1 means “no reading”, it must be skipped — and the divisor changes with it:

    int sum = 0, k = 0;
    for (int h = 0; h < H; h++) {
        if (temp[s][h] == -1) continue;        /* not a temperature */
        sum += temp[s][h];
        k++;                                   /* count only what we counted */
    }
    printf("average = %.1f over %d readings\n", sum / (double) k, k);
average, -1 treated as DATA    -> 186.5   over 8 readings
average, -1 treated as MISSING -> 213.3   over 7 readings

lowest reading, as DATA        -> -1 °C
lowest reading, as MISSING     -> 180 °C

Twenty-seven degrees apart, and the array is identical. The bits in memory do not know which they are. Only the person who built the rig knows — and if they did not tell you, your program is a guess wearing the costume of an answer.

You have met this before without noticing. On Monday, -999999 meant “this record is corrupt”. In a bank, a balance of -1000 might be a perfectly ordinary overdraft on one account and a serious bug on another — the same number, in the same column, meaning opposite things. There is no rule of C that will tell you which. There is only asking.

ImportantThe point of this course, in one paragraph

Programming is the means. The for loop, the second index, the continue — all of it is machinery for carrying out a decision that was already made, somewhere, by somebody.

The decision is the hard part. “Which sensor is hottest” is not a programming problem; it is a question that has not finished being asked. Your first job on any real task is to turn it into one that can be programmed — and that means going back to whoever asked and finding out what they meant. That is not a delay before the work. It is the work.

This matters more now, not less. A machine will write you the loop for any of the six readings above, quickly and correctly, and it will not ask you which one you wanted. It cannot: it has never seen your rig. What it produces is only ever as good as the question you handed it — so the person who can state the problem precisely is the one in control, and the person who cannot is merely typing.

It is also the only way to check the answer. You cannot verify a program against a question that does not have one answer. Specification and verification are the same skill, seen from either end, and interpretation is where both of them start.

Questions to Bring Back

For each of these, do not write code yet. Write down what the question could mean, pick one, and say in a sentence why you picked it.

  1. “Is the rig stable?”
  2. “Did probe 103 fail?”
  3. “What is the rig’s normal operating temperature?”
  4. “Which hour should we investigate?”
  5. A reading arrives as 999. The probes are rated to 340. Is that a real excursion, a stuck sensor, or a missing value someone encoded badly? What would you have to know, and who would you ask?

After Class

  • Type and run all eight. Where the machine disagrees with your prediction, find the rule you misapplied.
  • Answer with an array what you cannot answer without one: what was the average balance over the month? And the average of the changes — can you predict that answer before computing it?
  • Break it on purpose: change a loop bound to i <= n and describe what you get. If it did not crash — explain why that does not make the access correct.
  • The corrupted record again: §5 skipped it when finding the minimum. What does §7 do with it? Is skipping the right answer there too, or is something else needed?
  • A question we have not asked: on how many days was the balance above its own monthly average? Note that this one needs two passes over the array. Why can it not be done in one?

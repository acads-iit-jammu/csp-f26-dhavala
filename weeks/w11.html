Code You Can Copy

Every program below was compiled with gcc -Wall -Wextra and run, and the output shown is what it actually printed.

Monday

0 · Recap — strings, on one page

A string is an array of characters ending in '\0'. Everything else follows from that. Here is the whole of what you need, in one program, before we move on.

This is also the page to revise from for Class Test-2 — along with the W09 and W10 notes, since the test covers all three weeks.

#include <stdio.h>
#include <string.h>

int main(void)
{
    char a[100], b[50];       /* a must hold BOTH words, so it is the bigger one */

    printf("Enter two words: ");
    if (scanf("%49s %49s", a, b) != 2) return 1;

    printf("a = \"%s\", length %zu\n", a, strlen(a));
    printf("b = \"%s\", length %zu\n", b, strlen(b));

    if (strcmp(a, b) == 0) printf("they are the same word\n");
    else                   printf("they are different words\n");

    strcat(a, b);
    printf("joined: %s\n", a);
    return 0;
}

Typing level level:

a = "level", length 5
b = "level", length 5
they are the same word
joined: levellevel
scanf("%49s", a) reads one word, stopping at the first space. No & — an array name is already an address, which is why this differs from scanf("%d", &n). The 49 is one less than the array size and is not optional: plain %s will write past the end
strlen(a) how many characters come before the '\0' — so always one less than sizeof a for an array that is exactly full. It walks the array to find out, which is why it still works after the array has been passed to a function and sizeof no longer does
strcat(a, b) appends b onto the end of a, moving the terminator. a must already have room; nothing checks. strcpy(a, b) is the same but overwrites rather than appends
strcmp(a, b) zero means equal — so if (strcmp(a, b)) runs when they differ, which is almost always a bug. Write == 0 when you mean “the same”

Two of these carry most of the mistakes. scanf is the one where the missing & is correct — an array name is already an address — and strcmp is the one whose return value reads backwards.

The strings reference sheet has the rest on one page, including the character tests that Lab 08’s e1 and e4 need.

1 · A record is more than one value

A student has a roll number, a name and a mark. Three arrays kept in step is one way:

int    roll[50];
char   name[50][20];
double marks[50];

It works, and it is miserable. Nothing links roll[7] to name[7]; sorting means moving three arrays together; adding a field means changing every function. A structure gives the three fields one name:

struct Student {
    int  roll;
    char name[20];
    double marks;
};

That declares a type, not a variable — it reserves no storage. It says what a struct Student is made of.

2 · Making one and using it

#include <stdio.h>

struct Student {
    int  roll;
    char name[20];
    double marks;
};

int main(void)
{
    struct Student s;

    s.roll = 42;
    snprintf(s.name, sizeof s.name, "%s", "Asha");
    s.marks = 91.5;

    printf("roll  = %d\n", s.roll);
    printf("name  = %s\n", s.name);
    printf("marks = %.1f\n", s.marks);
    return 0;
}
roll  = 42
name  = Asha
marks = 91.5

The . reaches a member. s.roll is an int and behaves like any other int.

Note the name is set with snprintf, not =. s.name is an array, and you cannot assign to an array — s.name = "Asha" does not compile. To fill that member on its own, copying the characters in is the only way. There is one way round it, and it is worth waiting for: assigning a whole structure copies the name too, with no copying function at all. That is §3.

snprintf is new, and so is reading a name in from the keyboard without it going wrong. Neither is really about structures, so both are in the appendix at the end of these notes. Lab 09 does not require it — its names are single words, which %19s reads — but it is what you will need the first time a name has a space in it. For now all you need is that snprintf(s.name, sizeof s.name, "%s", text) is printf writing into a character array instead of onto the screen, and that it cannot overrun the array.

You can also set the members at the point of declaration, in order:

struct Student s = { 42, "Asha", 91.5 };

3 · A structure is a value: it copies

#include <stdio.h>
struct Point { int x, y; };
int main(void)
{
    struct Point a = { 1, 2 };
    struct Point b = a;          /* a whole-structure copy */
    b.x = 99;
    printf("a.x = %d   b.x = %d   (assignment copies every member)\n", a.x, b.x);
    printf("sizeof(struct Point) = %zu, two ints = %zu\n", sizeof(struct Point), 2*sizeof(int));
    return 0;
}
a.x = 1   b.x = 99   (assignment copies every member)
sizeof(struct Point) = 8, two ints = 8

Unlike an array, a structure can be assigned, and the assignment copies every member. This is worth noticing, because it is the one place C copies a compound object for you.

Which means a name can be assigned after all

Look at what that buys you when a member is an array. Everything below is a single line, and there is no strcpy, no snprintf, no fgets anywhere in the program:

#include <stdio.h>

struct Student {
    int  roll;
    char name[20];
    double marks;
};

int main(void)
{
    struct Student a = { 42, "Asha", 91.5 };   /* 1 - set up at declaration   */

    struct Student b;
    b = a;                                     /* 2 - whole-structure copy    */
    b.roll = 43;                               /*     only the roll differs   */

    struct Student c;
    c = (struct Student){ 77, "Ravi Kumar", 88.0 };   /* 3 - a fresh record,
                                                             in one line      */

    printf("a: %d %s %.1f\n", a.roll, a.name, a.marks);
    printf("b: %d %s %.1f\n", b.roll, b.name, b.marks);
    printf("c: %d %s %.1f\n", c.roll, c.name, c.marks);
    return 0;
}
a: 42 Asha 91.5
b: 43 Asha 91.5
c: 77 Ravi Kumar 88.0

Three things to take from it.

b = a copied the name. b.name holds "Asha" and nobody called a copying function. The twenty bytes were copied because they are part of the structure, and the structure was assigned.

Form 3 is new notation. (struct Student){ 77, "Ravi Kumar", 88.0 } builds an unnamed struct Student on the spot and assigns it. The braces list the members in declaration order, exactly as in form 1 — the difference is that form 1 only works at the declaration, while this one works at any point afterwards. It is the one-line way to overwrite a whole record.

None of this contradicts §2. b.name = a.name still does not compile:

b.name = a.name;     /* error: array type 'char[20]' is not assignable */

The array member cannot be assigned on its own. The structure containing it can, and when it is, the array goes along with it. That is the whole distinction — and it is why you reach for snprintf when you are filling in one field, and for = when you have a whole record to hand.

You still cannot compare two structures:

if (a == b)     /* error: invalid operands to binary expression */

Compare the members you care about, one at a time.

4 · Passing one to a function

A structure is passed by value, like an int — the function gets a copy, and changes to it are lost:

#include <stdio.h>

struct Point { int x, y; };

void moveCopy(struct Point p)    { p.x = 99; }          /* gets a copy      */
void moveReal(struct Point *p)   { p->x = 99; }         /* gets the address */

int main(void)
{
    struct Point a = { 1, 2 };

    moveCopy(a);
    printf("after moveCopy(a),  a.x = %d\n", a.x);

    moveReal(&a);
    printf("after moveReal(&a), a.x = %d\n", a.x);

    printf("(*p).y and p->y mean the same thing: %d\n", a.y);
    return 0;
}
after moveCopy(a),  a.x = 1
after moveReal(&a), a.x = 99
(*p).y and p->y mean the same thing: 2

This is exactly W10’s rule, now applied to a bigger object. To change the caller’s structure, pass its address.

And the arrow. When you have a pointer to a structure, reaching a member needs the pointer dereferenced first. *p.x does not work, because . binds tighter than * — it would mean *(p.x). You would have to write (*p).x, and that is so common C gives it a shorthand:

p->x means (*p).x

Use . when you have the structure, -> when you have a pointer to it.

There is a second reason to pass by address. A struct Student here is 32 bytes; a larger record might be hundreds. Passing by value copies all of it on every call. Passing a pointer copies 8 bytes whatever the structure’s size.

4b · A worked problem: is this point inside this rectangle?

Everything so far has been machinery. Here is a small problem that uses it, and it is the one we will do in class.

A structure can hold another structure. A rectangle, for our purposes, is fixed by two corners — and a corner is a point, which we already have:

struct Point { int x, y; };

struct Rect {
    struct Point lo;            /* bottom-left corner */
    struct Point hi;            /* top-right corner   */
};

struct Rect contains two struct Points, so reaching a coordinate takes two steps: r.lo is a struct Point, and r.lo.x is the int inside it. Read it left to right — the rectangle’s low corner’s x.

struct Rect box = { {0, 0}, {4, 3} };    /* braces inside braces: one per member */
printf("%d\n", box.hi.x);                /* 4 */

The question. Given a rectangle and a point, is the point inside? Say the edge counts as inside. A point is inside exactly when its x lies between the two x limits and its y lies between the two y limits — four conditions, all of which must hold:

int inside(struct Rect r, struct Point p)
{
    return p.x >= r.lo.x && p.x <= r.hi.x &&
           p.y >= r.lo.y && p.y <= r.hi.y;
}

Two things worth noticing. The function takes two whole structures by value — six ints copied in total (four in the rectangle, two in the point), which is nothing, and it does not modify either, so there is no reason to pass addresses here (§4). And it returns int used as a yes/no: 1 for inside, 0 for outside, which is how C has answered every true/false question since W06.

#include <stdio.h>

struct Point { int x, y; };

struct Rect {
    struct Point lo;            /* bottom-left corner */
    struct Point hi;            /* top-right corner   */
};

/* 1 if p is inside r, 0 if not. A point on the edge counts as inside. */
int inside(struct Rect r, struct Point p)
{
    return p.x >= r.lo.x && p.x <= r.hi.x &&
           p.y >= r.lo.y && p.y <= r.hi.y;
}

int main(void)
{
    struct Rect  box      = { {0, 0}, {4, 3} };
    struct Point tests[5] = { {2, 1}, {5, 1}, {0, 0}, {4, 3}, {2, 4} };
    int i;

    printf("rectangle: (%d,%d) to (%d,%d)\n\n",
           box.lo.x, box.lo.y, box.hi.x, box.hi.y);

    for (i = 0; i < 5; i++) {
        if (inside(box, tests[i]))
            printf("(%d, %d)  inside\n",  tests[i].x, tests[i].y);
        else
            printf("(%d, %d)  outside\n", tests[i].x, tests[i].y);
    }
    return 0;
}
rectangle: (0,0) to (4,3)

(2, 1)  inside
(5, 1)  outside
(0, 0)  inside
(4, 3)  inside
(2, 4)  outside

Look at which test points were chosen, because choosing them is half the work:

Point Why it is in the list
(2,1) plainly inside — the easy case
(5,1) x too large, y fine — catches checking only one coordinate
(0,0) the low corner itself — the edge case our rule says is inside
(4,3) the high corner — the other edge
(2,4) x fine, y too large — the mirror of the second

A test set that is all easy cases proves nothing. Two of these five sit exactly on the boundary, which is where >= against > decides the answer — and where this program would be wrong if we had meant strictly inside.

To try. Change both >= to > and both <= to <, and re-run. Which lines change? That one-character difference is the whole distinction between inside and strictly inside, and it is the kind of thing a specification has to say out loud.

5 · Arrays of structures

This is where the three-parallel-arrays problem disappears.

#include <stdio.h>
#include <string.h>

struct Student {
    int  roll;
    char name[20];
    double marks;
};

/* fills in one student through a pointer; returns nothing */
void readStudent(struct Student *s, int roll, char name[], double marks)
{
    s->roll = roll;
    strcpy(s->name, name);
    s->marks = marks;
}

double average(struct Student list[], int n)
{
    double total = 0.0;
    for (int i = 0; i < n; i++)
        total += list[i].marks;
    return total / n;
}

int main(void)
{
    struct Student cls[3];

    readStudent(&cls[0], 11, "Asha",  91.5);
    readStudent(&cls[1], 12, "Bilal", 78.0);
    readStudent(&cls[2], 13, "Chen",  84.5);

    for (int i = 0; i < 3; i++)
        printf("%d %-6s %.1f\n", cls[i].roll, cls[i].name, cls[i].marks);

    printf("average = %.2f\n", average(cls, 3));
    return 0;
}
11 Asha   91.5
12 Bilal  78.0
13 Chen   84.5
average = 84.67

Three things to read off that program.

cls is an array like any other. It is passed to average as a pointer and needs its length, exactly as in W10 §7. Nothing new.

list[i].marks has no arrow, because list[i] is a structure, not a pointer. s->roll does, because s is one.

&cls[0] is the address of one element — the same & on an array element you used in Lab 07’s swap(&a[lo], &a[hi]).

6 · One thing that will surprise you

struct Pad { char c; int n; };
char+int struct = 8, members sum to 5

A structure can be larger than its members added up. The compiler inserts unused bytes so that each member starts at an address the machine can read efficiently — here, three bytes after the char so the int starts at a multiple of 4. This is called padding.

You do not need to control it. You do need to know that sizeof(struct X) is the authority and arithmetic on member sizes is not. The GNU C Reference Manual says as much:

The size of a structure type is equal to the sum of the size of all of its members, possibly including padding to cause the structure type to align to a particular byte boundary.

Tuesday — File Input and Output

7 · The same reading and writing, with a name attached

Everything you have written so far reads from the keyboard and writes to the screen. Those are just two streams the program is handed when it starts. A file is the same idea with a name, and you open and close it yourself.

Four functions, and you already know two of them in another form:

fopen(name, mode) opens the file, hands back a FILE *
fclose(f) flushes everything still buffered to the system, then closes the stream
fprintf(f, …) exactly printf, with the stream as the first argument
fscanf(f, …) exactly scanf, with the stream as the first argument

The mode is a string:

Mode Means
"r" read. The file must already exist
"w" write. Creates the file, and empties it if it exists
"a" append. Creates if needed, writes at the end

"w" discards whatever was in the file, immediately, before you write anything. Opening your data file with "w" instead of "r" destroys it.

8 · Writing a file

#include <stdio.h>

int main(void)
{
    FILE *f = fopen("marks.txt", "w");      /* "w" = write, start empty */

    if (f == NULL) {
        printf("could not open marks.txt for writing\n");
        return 1;
    }

    fprintf(f, "%d %s %.1f\n", 11, "Asha",  91.5);
    fprintf(f, "%d %s %.1f\n", 12, "Bilal", 78.0);
    fprintf(f, "%d %s %.1f\n", 13, "Chen",  84.5);

    fclose(f);
    printf("wrote marks.txt\n");
    return 0;
}
wrote marks.txt

and marks.txt now holds:

11 Asha 91.5
12 Bilal 78.0
13 Chen 84.5

fprintf(f, …) is printf with one extra argument at the front. Everything you know about %d, %s and %.1f carries over unchanged.

9 · FILE * is a pointer, and it can be NULL

FILE *f = fopen("no-such-file.txt", "r");
if (f == NULL) { … }
fopen returned NULL — the file is not there

fopen is the one library call in this course that routinely fails, and it fails for ordinary reasons: the file does not exist, the name is misspelt, you are in the wrong directory, you lack permission. It does not crash — it returns NULL, and your program crashes later if you ignore that.

Check it every time. The NULL from W10 §8 is doing real work here.

10 · Reading a file back

#include <stdio.h>

int main(void)
{
    FILE *f = fopen("marks.txt", "r");      /* "r" = read */
    int roll, n = 0;
    char name[20];
    double marks, total = 0.0;

    if (f == NULL) {
        printf("could not open marks.txt for reading\n");
        return 1;
    }

    while (fscanf(f, "%d %19s %lf", &roll, name, &marks) == 3) {
        printf("%d %-6s %.1f\n", roll, name, marks);
        total += marks;
        n++;
    }

    fclose(f);

    if (n > 0)
        printf("read %d students, average %.2f\n", n, total / n);
    return 0;
}
11 Asha   91.5
12 Bilal  78.0
13 Chen   84.5
read 3 students, average 84.67

The loop condition is the whole technique. fscanf returns how many items it filled, so == 3 means “I got a complete record”. When the file runs out it returns EOF and the loop stops. You do not need to know the number of lines in advance, and you do not need a sentinel value at the end of the file.

That is the same return value you were told to check for scanf in §0 — here it is earning its keep.

Note %19s again, and &roll and &marks but no & on name. fscanf follows exactly the same rules as scanf, because it is scanf with a stream argument.

10b · What EOF actually is

The loop above stops “when the file runs out”, and it is worth being exact about what that means, because the usual picture of it is wrong.

There is no EOF character in the file. Look at a one-record file byte by byte:

$ printf '11 Asha 91.5\n' > one.txt
$ wc -c < one.txt
13
$ od -c one.txt
0000000   1   1       A   s   h   a       9   1   .   5  \n
0000015

Thirteen bytes: the twelve you can see, and the newline. There is no thirteenth marker, no special byte at the end. The file simply stops.

So EOF is not something in the data. It is a value the library hands back to you to say “there was nothing left to read”. It is a macro from stdio.h. The standard guarantees only that it is negative; in practice, everywhere you are likely to meet, it is -1:

printf("EOF is the value %d\n", EOF);     /* EOF is the value -1 */

It is negative on purpose: a count of successfully read items can be 0, 1, 2, …, so a negative value is free to mean something different without ever colliding with a real answer.

What fscanf returns, in every case

That gives fscanf four distinct things to tell you, and the difference matters:

Your file holds fscanf(f, "%d %19s %lf", …) returns Meaning
11 Asha 91.5 3 a complete record
11 Asha 2 partial — two fields matched, the third ran out
hello there 0 nothing matched: the first conversion already failed
(nothing left) EOF input ended, or failed, before the first conversion

All four were produced by running exactly that call on exactly those files.

Two refinements worth knowing. EOF comes back only when the input ends before the first conversion — if it ends partway through, you get the count so far, which is the 2 in the second row. And EOF does not distinguish “the file ended” from “the read failed”: for that there is feof(f) against ferror(f). For a file you opened yourself and are reading to the end, the end is overwhelmingly the reason, which is why == 3 is enough for this course.

This is why the loop is written == 3 and not != EOF. != EOF would keep going on a partial or malformed record, using whichever variables happened to be filled and whatever junk was in the rest. == 3 means “I got everything I asked for”, and stops for any other reason — clean end, short line, or rubbish.

10c · fscanf does not read lines

Here is the misconception worth spending a minute on. fscanf looks line-oriented because our file has one record per line. It is not. fscanf reads conversions, not lines, and %d, %s and %lf each begin by skipping over any amount of whitespace — spaces, tabs, and newlines alike.

A newline is simply whitespace. fscanf cannot see the difference between these five files:

layout A       layout B                    layout C      layout D          layout E
11 Asha 91.5   11 Asha 91.5 12 Bilal 78.0  11            11⇥Asha⇥91.5        11   Asha    91.5
12 Bilal 78.0                              Asha          12⇥Bilal⇥78.0
                                           91.5                               12  Bilal 78.0
                                           12
                                           Bilal
                                           78.0

One record per line; both records on one line; one field per line; tab-separated; and ragged with blank lines. Running the same loop — while (fscanf(f, "%d %19s %lf", &roll, name, &marks) == 3) — on each of the five gives the identical answer every time:

got: 11 Asha 91.5
got: 12 Bilal 78.0
-> 2 records

Two consequences, one convenient and one dangerous.

The convenient one: you never have to worry about how the data is spread across lines, or about extra blank lines, or about whether someone used tabs. Whitespace is whitespace.

The dangerous one: a missing field does not stop at the end of the line. If one record is short, fscanf walks straight onto the next line looking for what it is owed, and from then on every record is shifted by one field. The file is not corrupt and the program does not crash — the answers are just quietly wrong. If that matters to you, read a line at a time instead (§10e).

10d · When the layout does matter: separators

Everything above works because the fields are separated by whitespace and no field contains any. Break the second half of that and the whole approach collapses:

11 Ravi Kumar 91.5
-> 0 records

Not one record, not a wrong record — zero. %19s reads Ravi and stops at the space, then %lf is handed Kumar and fails, so the count is 2, not 3, and the loop never starts. A name with a space in it cannot be read by whitespace-separated conversions, and no amount of care with %s will fix it: the separator and the data have become the same character.

The fix is to choose a separator the data cannot contain, and say so in the format. %19[^,] means “up to 19 characters, none of which is a comma” — a set, not a word:

File Format that reads it
11,Ravi Kumar,91.5 "%d,%19[^,],%lf"
11⇥Ravi Kumar⇥91.5 (tabs) "%d\t%19[^\t]\t%lf"

Both give [11] [Ravi Kumar] [91.5]. The work is done by the scan set %19[^,], which reads characters until it meets one it was told to exclude, rather than stopping at the first space.

The comma in that format is matched literally. The \t in the other one is not. Any whitespace character in a format — a space, a \t, a newline — is a whitespace directive: it matches any run of whitespace, including none at all. So the tab format above will happily read a space-separated line too:

fscanf(f, "%d\t%19[^\t]\t%lf", &roll, name, &m);   /* on "11 Ravi Kumar 91.5" */

The %d takes 11, the \t matches the space, and %19[^\t] then swallows Ravi Kumar 91.5 whole, because it excludes only tabs. The call returns 2.

If a separator must really be there, it has to be a character that is not whitespace — a comma, a semicolon, a |. For genuinely tab-separated data, read the line with fgets and split it yourself (§10e).

Fixed-width columns

Some data has no separators at all — just columns at known positions, which is how a great deal of older scientific and administrative data is stored:

011Asha      091.5
012Bilal     078.0

A number between % and the letter is a maximum field width measured in characters, not digits: %3d consumes at most three characters, and a minus sign is one of them, so %3d on -12 reads −12 and on -123 reads only −12. %10c takes ten characters whatever they are.

Two cautions. %3d still skips leading whitespace first, so it is not strictly positional — it finds the next number and then limits how much of it it takes. And a width is a maximum, not a requirement: %10c against a two-character line succeeds with two. Fixed-width parsing therefore assumes the columns really are complete and in place; check the return value before trusting the fields.

sscanf(line, "%3d%10c%5lf", &roll, name, &m);
name[10] = '\0';                 /* %c does NOT add a terminator - you must */
roll=11 name=[Asha      ] marks=91.5
roll=12 name=[Bilal     ] marks=78.0

Two things to notice: %c does not append '\0', so you add it yourself, and the name keeps its padding spaces, because in fixed-width data the padding is the field. Trim it if you need to.

10e · The other way: one line at a time

When the data really is line-oriented — when a short line should be reported rather than silently absorbed into the next — read lines yourself and parse each one separately. sscanf is scanf reading from a string instead of a stream, so the format you already know carries over unchanged:

#include <stdio.h>

int main(void)
{
    FILE *f = fopen("ragged.txt", "r");
    char line[256];
    int lineno = 0, good = 0;
    int roll;  char name[20];  double m;

    if (f == NULL) { printf("could not open ragged.txt\n"); return 1; }

    while (fgets(line, sizeof line, f) != NULL) {
        lineno++;
        if (line[0] == '\n') continue;                    /* blank line */


        if (sscanf(line, "%d %19s %lf", &roll, name, &m) == 3) {
            good++;
            printf("line %d ok : %d %s %.1f\n", lineno, roll, name, m);
        } else {
            printf("line %d BAD: %s", lineno, line);      /* line keeps its \n */
        }
    }

    fclose(f);
    printf("-> %d good of %d lines\n", good, lineno);
    return 0;
}

Give it a ragged.txt that is deliberately messy — a blank line, a line that is not a record at all, and a record missing its last field:

11 Asha 91.5

this line is broken
12 Bilal 78.0
13 Chen
line 1 ok : 11 Asha 91.5
line 3 BAD: this line is broken
line 4 ok : 12 Bilal 78.0
line 5 BAD: 13 Chen
-> 2 good of 5 lines

fgets reads at most sizeof line - 1 characters, stopping early at a newline. So one call is one line only while the lines are shorter than the buffer: give it a line of 300 characters and a 256-byte buffer, and you get that line in two pieces, counted as two. It keeps the '\n' when it found one — and the last line of a file need not have one at all. It returns the buffer on success and NULL when it read nothing, whether because the file ended or because the read failed.

For this course, sizing the buffer comfortably above the longest line you expect is the whole of the technique.

That is the whole reason to prefer it: a bad line is confined to its line, and you can say which one. Run the fscanf loop of §10 on the same file and it reports one record and stops — it reaches this line is broken, fails to convert this to an int, and ends the loop. The two perfectly good records further down are never seen, and nothing says so.

Use fscanf on the stream Use fgets + sscanf
Layout may be spread any way over lines one record per line
A bad record stops the loop, silently reported, with its line number, and skipped
Fields with spaces impossible possible, and you control the splitting
Code one line a loop and a check

For Lab 09 either will do, because the roster is well formed and names are one word. Know that the second exists for when they are not.

11 · Putting it with structures

Monday’s struct Student and Tuesday’s file are the obvious pair — a file of records read into an array of structures:

struct Student cls[50];
int n = 0;

while (n < 50 &&
       fscanf(f, "%d %19s %lf", &cls[n].roll, cls[n].name, &cls[n].marks) == 3)
    n++;

&cls[n].roll is the address of one member of one element. The n < 50 guard comes first so that a longer file cannot run past the end of the array — the file decides how much data arrives, and your array does not grow.

12 · What goes wrong

not checking fopen the commonest file bug by a distance; the program dies later, far from the cause
opening with "w" to read silently empties the file first
forgetting fclose data can sit in a buffer unwritten; returning from main flushes it, but a crash or _exit does not
looping on !feof(f) processes the last record twice — see below
no bound when filling an array a long file writes past the end
relative paths "marks.txt" means in the directory you ran the program from, not where the source lives
WarningWhy while (!feof(f)) is wrong

It reads plausibly — “while we are not at the end of the file” — and it is the single most common file-handling bug in C. Put just two records in a file — 11 Asha 91.5 and 12 Bilal 78.0, each on its own line — and read it like this:

while (!feof(f)) {
    fscanf(f, "%d %19s %lf", &roll, name, &marks);
    printf("iteration %d: %d %s %.1f\n", ++n, roll, name, marks);
}
iteration 1: 11 Asha 91.5
iteration 2: 12 Bilal 78.0
iteration 3: 12 Bilal 78.0        <- the last record, again
-> 3 iterations for 2 records

The reason is the order of events. feof does not look ahead; it reports a flag that is set only after a read has already run off the end. After the second record the file still holds its final newline, and nothing has tried to read past it, so the flag is clear and feof is false. The loop runs once more, that fscanf finally fails, and because its return value is being ignored, roll, name and marks are left holding the previous record — which is printed again as if it were new.

The duplicate is the common symptom, not the only one. On a file whose next line is not a record at all, fscanf returns 0 without reaching the end, so the flag is never set and the same bad line is retried forever.

Test the read, not the stream: while (fscanf(...) == 3) asks the question at the moment it can actually be answered.

Appendix · Copying names safely

Not about structures. It is here because struct Student has a char name[20] in it, and getting text into a fixed-size array without losing part of it — or running off the end — is a separate skill with its own traps. Kept out of the main sections so that those can be about records. You need this for Lab 09’s e2.

New here: snprintf

snprintf is printf that writes into a character array instead of onto the screen. Same format strings, same %d and %s and %.2f — different destination.

snprintf(where, how_big, "format", ...);
Argument Meaning
where the character array to write into
how_big its total size in bytes — snprintf will never write more than this
"format", ... exactly as in printf 
char small[8];
snprintf(small, sizeof small, "%s", "Asha");        /* small is now "Asha"    */
snprintf(small, sizeof small, "%s-%d", "ID", 42);   /* small is now "ID-42"   */

Why the size argument matters. strcpy(s.name, "Asha") does the same job here and is shorter, but it takes no size, so it cannot refuse. Hand it a name longer than the array and it writes straight past the end into whatever is next — the classic C bug, and undefined behaviour. snprintf cannot do that. It copies what fits, terminates with '\0', and stops:

char small[8];
snprintf(small, sizeof small, "%s", "Parvinder");   /* small is "Parvind"     */

Seven characters and the terminator: eight bytes, exactly the size you declared. Truncated, but never out of bounds.

Write the size as sizeof, not as a number you typed. For the struct Student of §2, whose name member is char name[20], sizeof s.name is 20 — and it stays correct by itself if you later widen the field to char name[40]. A hand-written 20 would quietly become wrong.

One catch, from W10 §7. sizeof only gives you the array’s real size where the array is declared. Inside a function that received it as a parameter it is a pointer, and sizeof gives 8 — the size of the address, not of the 20 bytes behind it. So in a function like void setName(char dest[], int n), the length must still be passed in as n, exactly as it was for every array function you wrote in W09.

The two returns are not quite the same thing. printf gives the number of characters it actually sent. snprintf gives the length the result would have had, not counting the terminator — which is exactly what makes it useful: a return of 26 from a buffer of 20 is how you learn that truncation happened. Both return a negative value if the formatting itself fails, in which case do not use what is in the buffer.

snprintf is declared in stdio.h, which you already include; strcpy needs string.h.

Reading a name in, properly

So far the name has always been one we wrote into the program ourselves — "Asha", in a line of source. Real input is harder, and it is worth doing once, carefully, because three separate things can go wrong.

First: scanf("%s") cannot read a full name. %s stops at the first whitespace.

char name[20];
scanf("%19s", name);        /* input: Ravi Kumar */
printf("[%s]\n", name);     /* prints [Ravi] — "Kumar" is still waiting */

For a line that may contain spaces, use fgets, which reads up to a newline:

char line[100];
fgets(line, sizeof line, stdin);

Second: fgets keeps the newline. If you type Ravi Kumar and press Enter, line holds Ravi Kumar\n. Left alone, that newline is stored in the record and prints as a stray line break later. Remove it if it is there:

size_t len = strlen(line);
if (len > 0 && line[len - 1] == '\n') {
    line[len - 1] = '\0';
    len--;
}

The len > 0 guard matters: on an empty line there is no character to examine, and line[len - 1] with len == 0 would read line[-1].

Third: the name may not fit. s.name holds 20 bytes, one of which must be the terminator — so 19 characters at most. You now have a decision to make, and it is a design decision, not a syntax one:

What it does When it is right
Truncate store the first 19 characters and carry on the field is a display label; a shortened name is better than no record
Refuse reject the input and ask again the name is data that must be correct — a mark sheet, a certificate

C gives you a clean way to do each.

Truncating: let snprintf do it, then ask what happened

This is where the return value earns its place. snprintf never overflows, and it reports: it returns the length the result would have had, so a value at or beyond the size tells you characters were dropped.

int n = snprintf(s.name, sizeof s.name, "%s", line);

if (n < 0) {
    printf("formatting error — nothing was stored\n");
}
else if ((size_t) n >= sizeof s.name) {
    printf("name truncated: needed %d bytes, the field holds %zu\n",
           n + 1, sizeof s.name);
}

Three details worth being exact about:

  • n < 0 is a genuine failure inside snprintf (an encoding error), not a size problem. Nothing useful was stored.
  • n counts characters without the terminator, so the space actually needed is n + 1.
  • The cast (size_t) n is not decoration. n is a signed int and sizeof is an unsigned size_t; comparing them directly makes gcc -Wextra say “comparison of integers of different signs”. Cast the one you know is non-negative — which is why this comparison sits after the n < 0 test.

Refusing: measure first, then strcpy

The box above said strcpy takes no size and so cannot refuse an oversized name. That is true, and it is the whole of the objection: it describes strcpy used unchecked. A function that cannot refuse does not need to, once you have already established that the string fits. So measure, decide, then copy:

if (strlen(line) >= sizeof s.name) {
    printf("name is %zu characters; the field holds %zu including the terminator\n",
           strlen(line), sizeof s.name);
    return 1;                       /* refuse — nothing is stored */
}
strcpy(s.name, line);               /* safe: we just proved it fits */

>= and not > is the whole boundary. sizeof s.name is 20, so a 19-character name needs 20 bytes and just fits; a 20-character name needs 21 and does not.

The whole thing

#include <stdio.h>
#include <string.h>

struct Student {
    int  roll;
    char name[20];
    double marks;
};

int main(void)
{
    struct Student s;
    char line[100];
    size_t len;
    int n;

    printf("Name: ");
    if (fgets(line, sizeof line, stdin) == NULL) {
        printf("could not read a name\n");
        return 1;
    }

    len = strlen(line);
    if (len > 0 && line[len - 1] == '\n') {
        line[len - 1] = '\0';
    }

    n = snprintf(s.name, sizeof s.name, "%s", line);

    if (n < 0) {
        printf("formatting error — nothing was stored\n");
        return 1;
    }
    if ((size_t) n >= sizeof s.name) {
        printf("warning: name truncated — needed %d bytes, the field holds %zu\n",
               n + 1, sizeof s.name);
    }

    printf("stored: [%s]  (%zu characters)\n", s.name, strlen(s.name));
    return 0;
}

Run it four times, giving it something different each time. In each block below, the text after Name: is what you typed; every other line is the program’s own output.

1 · A name that fits. Type it and press Enter.

Name: Ravi Kumar
stored: [Ravi Kumar]  (10 characters)

2 · A name that does not fit. 26 characters offered, 19 stored.

Name: Subrahmanyan Chandrasekhar
warning: name truncated — needed 27 bytes, the field holds 20
stored: [Subrahmanyan Chandr]  (19 characters)

3 · Press Enter without typing anything. fgets succeeds — it read a line, and that line happens to be empty. The newline is stripped, line becomes "", and an empty name is stored. Note what does not happen: this is not an error, and the program has no way to tell it apart from a name of zero characters, because that is exactly what it is.

Name:
stored: []  (0 characters)

4 · Give it no input at all. Press Ctrl-D on an empty line — on Linux and macOS that signals end of input — or run the program with its input redirected from an empty file, ./a.out < /dev/null. There is now no line to read, so fgets returns NULL and the program stops instead of using line, which was never filled in.

Name: could not read a name

Cases 3 and 4 look similar on screen and are completely different underneath: in 3 fgets worked and gave you an empty string, in 4 it failed and gave you nothing at all. Checking fgets(...) == NULL is how you tell them apart, and it is why that check is the first thing in the program.

snprintf counts bytes, not words. The second name is cut after Chandr because that is where byte 19 falls — truncation has no idea what a word is, and will happily leave you half of one.

Notice the shape of that program, because it is the shape of most real input code: one line actually does the work, and the rest establishes that doing it is safe. That ratio does not mean something has gone wrong. It is what handling input looks like when you take the edges seriously — and the edges are where marks, and later data, are lost.

PAGAL — Perspectives on Algorithms, Generative AI & Learning: the week’s informal column.

The interview that does not ask you to write code.

In May 2026 Google began piloting a change to its software engineering interview. One of the traditional coding rounds — the kind you prepare for on LeetCode — was replaced with something called a code comprehension round. You are given a codebase you have never seen. You are given Gemini to help you. And you are asked to read it, find the bugs, explain the design decisions, and suggest what you would improve.

It reached us through a post by Shreyas Naphad on 10 October 2026, so — following the Week 1 habit — we checked it before repeating it.

Claim Standing
Google is piloting an AI-assisted round for junior and mid-level roles on select US teams confirmed; a Google spokesperson confirmed candidates use Gemini
The internal description is “human-led, AI-assisted” reported from an internal document
It evaluates prompt engineering, output validation, and debugging reported consistently
200–500 lines, 60 minutes, three phases in a CoderPad environment reported in secondary coverage; not an official Google figure

The precise numbers may drift. The direction will not, and the direction is the point.

A second account, and how to weigh it.

The news travelled loudly. The r/leetcode thread discussing it is titled “LeetCode grind is dead.” It is posted by a throwaway account claiming to be a Googler — which is to say, unverifiable. Read it anyway; it is where your seniors are arguing about your job. But weigh it correctly, and notice that weighing it correctly is the same skill the new round is testing.

The post claims Google is rolling out two AI Fluency rounds:

AI Debugging: Dropping you into a massive, messy legacy repo to see if you can actually use AI to locate, diagnose, and patch complex bugs in real time.

AI System Design: Architecting end-to-end systems while actively using AI to evaluate trade-offs, draft interfaces, and pressure-test edge cases.

And then: “Pure DSA won’t carry loops anymore.”

Now read the edit at the bottom of that same post: “2 DSA rounds will still be there, and it’s for all L3-L5 roles.”

That edit quietly demolishes the headline above it. Two algorithm rounds remain. Nothing here says stop learning loops, arrays, recursion or complexity — and it could not, because you cannot judge code you could not have written. An AI’s wrong answer looks exactly like its right answer until you know the subject well enough to tell them apart. That is the whole reason this course does not skip pointers, memory, or the compiler.

So: the anonymous claim is unverified, its headline overshoots, and its own correction contradicts it — and underneath all that it still agrees with the part Google actually confirmed. Hold all four of those thoughts at once. That is what reading critically looks like, and you will do it far more often with generated code than with Reddit posts.

What is dying is not the algorithms. It is the idea that reciting them is enough.

You already read more code than you write.

Clean Code opens with the claim that “the ratio of time spent reading versus writing is well over 10 to 1.” Treat that as an experienced assertion rather than a measurement — nobody ran a stopwatch on the industry. But you do not need the number, because you have your own evidence from this semester.

Count honestly. In Lab 07 — the Game of Life, the largest program you have written so far — how long did you spend typing, and how long did you spend staring at code that already existed? The starter file. The spec comment. Your partner’s countNeighbours. A compiler error pointing at line 23. Your own loop from twenty minutes ago that no longer looked familiar. The typing was the short part. It is always the short part.

What is new is not the ratio. What is new is the size of the thing you must read.

The blocks got bigger.

A 300-line file used to arrive slowly. Someone wrote it over days, you reviewed it in pieces, and you absorbed it at roughly the speed it was produced.

Now you can ask for 300 lines and have them in ten seconds. The production side got faster by orders of magnitude. Your reading speed did not change at all. That gap is the whole story of this decade, and it is why the interview moved.

This is also the honest reason your struct work this week matters more than it looks. Compare these two, which store the same thing:

int   rolls[100];      char  names[100][20];      double marks[100];
struct Student { int roll; char name[20]; double marks; };
struct Student cls[100];

The first is three arrays that you must personally remember to keep in step. The second says what it is. A reader meeting cls[i].marks knows something; a reader meeting marks[i] has to go hunting for whether i still means what it meant forty lines ago. You have just learned your first tool for making a large program readable — which is to say, your first tool for making a large program possible.

Taste and judgement are two different things.

The round asks for both, and it is worth separating them.

The question Can the machine answer it?
Judgement Is this correct? Does it hold at the edges, on empty input, when the file will not open? It can help — and it will also assert correctness confidently and be wrong
Taste Is this good? Is this the right decomposition, the right name, the right thing to store? No. It has no stake in who maintains this in two years

Judgement is the skill this course has been drilling since Week 1: predict the output before you run it, say what the function ensures, ask for the evidence. Taste is newer, and it is what structures start teaching you — not “does this compile” but “is this the right set of fields?” There is no compiler error for a bad design. There is only a program that becomes harder to change every week until somebody rewrites it.

Taste is built the slow way: by reading a great deal of code, by writing something badly and then having to extend it, and by noticing the difference. There is no prompt for it.

Architect is a job description, not a promotion.

The old career story was: write code for some years, and eventually you will be allowed to design systems. That ladder is being compressed from the bottom. The commodity rung — turn a clear specification into syntax — is the rung the machine now stands on.

What is left is the work above it: deciding what should exist, how the parts divide, what each part promises the others, and whether what came back is actually right. Week 1 called this Specify → Express → Verify, and said the machine took the middle step. The Google round is simply that claim showing up in a hiring process. They did not stop testing Express — the algorithm rounds are still there, as we just established. They added a round that tests Verify directly, with the machine sitting right there on the desk, which is harder to fake and much closer to the job.

Notice what the anonymous post called its second round: AI System Design — and note that it is claimed for L3, which is the level you would enter at. Architecting end-to-end systems, weighing trade-offs, drafting interfaces, pressure-testing edge cases. Whether or not that specific round exists as described, the shape of the claim is the shape every confirmed source points to: design work has moved down the ladder, to the first rung.

So the uncomfortable framing — you must become architects — is not career advice for your thirties. It is a description of the entry-level job.

Which is why a five-line struct declaration deserves more of your attention than it instinctively gets. Choosing what goes inside struct Student is a design decision with no compiler to check it: it is the smallest honest instance of the work above. You will not practise architecture by waiting for a big system. You practise it on the small ones, on purpose, now.

You have been sitting this round all semester.

Start with the part of the lab nobody grades. Open drill.sh and read the comment at the top of it:

Each drill: you SEE it, you WRITE your prediction, and only THEN does it run. Predicting is the exercise. Running is just the marking.

That is a code comprehension round. You are handed code you did not write, you are not allowed to execute it, and you must say what it does. No marks ride on it, which is exactly why it works: there is nothing to perform and nowhere to hide. When the drill logs a miss it tells you “logged as a miss — that is the useful kind. Ask why before moving on.” A miss is the only part of the lab that reliably teaches you something, because it is the precise location where what you believed about C and what C actually does came apart.

Be clear about the scale, though. A drill is a dozen lines and tests one idea — that a[i] is *(a+i), that strcmp returns zero for equal, that sizeof collapses to 8 inside a function. Google’s round is 200–500 lines of unfamiliar code with bugs hidden in the interactions between parts, and the hard thing there is not any single line but holding the whole shape in your head. The drills are that skill in miniature — the same move, at a fortieth of the scale.

But it is the same move, and it is the one that scales. Nobody reads a 500-line file by reading 500 lines. You read it by forming a guess about what a part does, checking the guess cheaply, and being willing to find out you were wrong. Every drill is one repetition of that loop. There have been drills in every pack since Lab 03, and by the end of Lab 07 you had done fifty-three of them. That is fifty-three times you committed to a claim about unfamiliar code before the machine told you the answer.

Then look at how the labs are actually graded. Band A is automated: your code compiles and passes the vectors. Band B is a person pointing at a line you submitted and asking you to explain it — and a member who cannot explain their own code resubmits, whatever the score says.

That is the same round again, with marks attached. We did not design it to imitate Google; we designed it because it is the only honest way to grade work that an AI could have produced. The industry arrived at the same instrument for the same reason. There is no trick to preparing for it, at Google or here. Read more code than you write. Be able to say what every line you submit is for. And when something works and you do not know why, treat that as an unfinished problem rather than a finished one.
